## 0. 先说清楚：这两道闸门不是「量一下就知道」

方案 §11.0 写「两道闸门都属于工程实测，预计各半天到一天」。**这个估算没有依据，按它排期会翻车。**

闸门 A 要测的是「带字幕带声音的整片连播」，而现有连播实现
（`app/weapp-native/packages/video/shots/index.js:534-637`）**刻意不做这件事**：

| 现状 | 闸门 A 要测的东西 |
|---|---|
| 单个 `<video muted loop autoplay>`，换 `src` 切段（`index.wxml:125`） | 要有音频主时钟，画面跟着音频走 |
| 用 `setTimeout(段时长)` 排下一段（`scheduleAdvance`） | `setTimeout` 不是时钟，它只保证「不早于」，累计漂移就是这么来的 |
| 无字幕轨 | 要真实字幕：文本、逐句时间窗、位置、样式 |
| 无预加载，切段即换 src 冷加载 | 要下一段预加载，否则切换间隙测的是网络不是播放器 |
| 无任何耗时埋点 | 要有埋点，否则「间隙 150ms」拿什么证明 |

**所以闸门 A 的真实顺序是：先做一个能测的东西（下称「A 装置」），再测。** A 装置不是产品代码，
是一次性 spike，但它是 §3.2 默认链路的原型，做完的结论直接决定第一档要不要做。

粗估（供排期用，不是承诺）：

| 工作项 | 量级 |
|---|---|
| A 装置：音频主时钟 + 字幕轨 + 双 `video` 实例交替预加载 + 埋点 | 3～5 人日 |
| 测试素材集准备（真实 TTS 整轨、22 段素材、对齐标记片） | 1 人日 |
| 跑测 + 逐帧分析 + 出报告 | 2 人日 |
| **闸门 A 合计** | **6～8 人日** |
| B 装置：360p 代理档 ffmpeg 管线 + 并发闸 + L3 overlay spike | 3～4 人日 |
| 跑测 + 出四个数 + 出报告 | 1～2 人日 |
| **闸门 B 合计** | **4～6 人日** |

闸门 B 稍轻，因为 AIStar 侧已有 `ClipAssemblyService`（`concat + drawtext + amix + 封面/片尾`），
代理档是在它旁边加一档输出参数，不是从零写管线。但**并发闸和 L3 overlay 都是新代码**，
方案 §5.5 已经写明「代理档、转场和并发闸都是新增工程量」。

## 1. 两道闸门共用的规则

任何一条测试数据，缺下面任一项就作废重跑。

### 1.1 机型：写规则，也写清单

低端安卓的「低端」必须可复现，不能各人拿各人手边的机器。

| 位号 | 选取规则 | 推荐机型（有就用这个，没有按规则替） |
|---|---|---|
| **A-low** | 2021–2022 发布、发布价千元档、SoC 为骁龙 4xx/6xx 或天玑 700 系、RAM ≤ 6GB | Redmi 10A / Redmi Note 11 / OPPO A56 |
| **A-mid** | 2023–2024 发布、中端 SoC（骁龙 7 系 / 天玑 8000 系）、RAM 8GB | Redmi Note 13 / OPPO K11 |
| **I-old** | 仍在微信支持范围内的最老一代、A13 及以下 | iPhone 11 / iPhone SE 2 |
| **I-new** | 当代 iPhone，做对照上限 | iPhone 15 / 16 |

**必须记录并写进报告**：具体型号、系统版本、微信版本号、小程序基础库版本、
测试时电量与是否插电、是否开省电模式（一律**关**省电模式并插电，否则安卓会降频）。

A-low 与 I-old 是判据机型，A-mid / I-new 只做对照，不参与过/不过的判定。

### 1.2 网络：三档，用 dummynet 整形，配置留档

手机侧无法可靠整形，用一台 Mac 开「互联网共享」，在共享出去的桥接口上挂 dummynet：

```bash
sudo dnctl pipe 1 config bw 10Mbit/s delay 30ms plr 0
echo 'dummynet out proto {tcp,udp} from any to any pipe 1' | sudo pfctl -f - -e
```

| 档位 | 参数 | 用途 |
|---|---|---|
| **W** 好网 | 不整形，实测下行 ≥ 50Mbps、RTT ≤ 30ms | 上限参考 |
| **M** 常态 | `bw 10Mbit/s delay 30ms plr 0`（单向 30ms → RTT 约 60ms） | **判据档** |
| **P** 弱网 | `bw 2Mbit/s delay 100ms plr 0.01` | 降级行为观察，不参与判定 |

判定只看 **M 档**。W 档过 M 档不过，等于「只有在办公室 Wi-Fi 才成立」，不算成立。

每次跑测前用 `speedtest` 或一次固定大小文件下载复核实际带宽，把实测值写进报告——
dummynet 配了不等于生效。

### 1.3 冷/热缓存：靠 URL，不靠清缓存

「清一下小程序缓存」不可复现（微信不保证清干净，CDN 边缘节点也还在）。改成：

- **冷缓存**：每次冷测用一组**带唯一签名 query 的素材 URL**（`?t=<本次跑测 ID>`），
  保证端上、CDN 边缘、运营商缓存三层都没有它。
- **热缓存**：同一组 URL 紧接着第二次完整连播，中间不退出页面。

冷/热各自独立统计，不合并。**判据看冷缓存**——用户第一次看片就是冷的。

### 1.4 统计口径：把 P95 的算法写死

不同工具的百分位算法能差出十几毫秒，必须统一：

- **线性插值法**（等价于 Excel `PERCENTILE.INC`、numpy `percentile(..., method='linear')`）。
- **先合并再算**：把一个格子（机型 × 网络 × 冷热）里所有跑次的所有样本合并成一个池子，
  在池子上算一次 P95。**不是**每跑一次算个 P95 再取平均——那样会把长尾抹掉。
- 除 P95 外，**必须同时报告 max**。P95 达标但 max 是 1.2 秒，说明有偶发大黑场，
  用户一次就看见了，这种不算过（见 §2.4 的双线判据）。

### 1.5 样本量

- 每个格子跑 **N = 10 次完整连播**。ct_shiti 22 段 → 每次 21 个切换间隙 → 每格 210 个间隙样本。
- 210 个样本足以判断「过 / 不过」，但不足以报告精确值。
  **若 P95 落在通过线 ±20ms 的灰区，该格子补跑到 N = 30 再判。**
- 首帧起播每格 N = 10（每次连播一个样本），落在灰区同样补到 30。
- 音画漂移每格 N = 10。

### 1.6 证据：端上埋点 + 60fps 录屏，双证据，冲突以录屏为准

端上埋点知道「代码认为它播了」，录屏知道「用户看见了什么」。两者会不一致，
而闸门 A 要回答的正是用户看见了什么。

**端上埋点**（A 装置必须打）：每段记录 `srcSetAt / firstFrameAt(bindplay) / advanceAt`，
音频主时钟每 500ms 采样一次 `audioCurrentTime` 与 `Date.now()`。

**录屏**：60fps 屏幕录制，**含内录音频**。

> ⚠️ **开跑前必须先验证录屏能录到小程序内音频**。iOS 屏幕录制与 Android 10+ 的
> `MediaProjection` 都支持内录，但机型和微信版本可能有限制。录不到就换外录
> （手机 3.5mm/Type-C 输出 → 采集卡），并在报告里注明音频通路，因为外录会引入固定延迟，
> 需要先用一个已知同步的参考片标定并从结果中扣除。**这一步没做，所有漂移数据都是废的。**

所有原始录屏、埋点 JSON、ffmpeg 分析脚本与输出，按 `跑测ID/机型/网络/冷热/` 归档留存，
报告里只放结论，但结论必须能追回到原始文件。

## 2. 闸门 A：手机装配预览可行性

### 2.1 测试内容用真的，不用编的

| 项 | 用什么 |
|---|---|
| 时间线 | **`ct_shiti` 全片**：22 段、163 秒、数字人段在第 1/7/13/21 段（`catalog.js` 运行时真值） |
| 音轨 | 按 §5.5「TTS 是预览的前置确定性输入」，**必须是真实生成的整条 163 秒 TTS**，不是占位音 |
| 字幕 | 真实逐句时间窗、真实字体与位置，不是静态贴图 |
| BGM | 真实 BGM 一轨，与 TTS 混音 |
| 数字人段（4 段 / 32 秒） | 从**一条已有的真实数字人成片**里切等时长片段顶上，保证有真人口型可判 —— **不为闸门新生成数字人** |
| b-roll 段（17 段 / 121 秒） | 真实上传素材，含至少 3 条竖屏手机拍摄、至少 2 条需要裁剪的横屏 |
| 尾片（1 段 / 10 秒） | 真实固定尾片 |

素材集固定下来后**不再改**，两台判据机型跑的必须是同一组文件。

### 2.2 对齐标记片（漂移测量的前提）

在上面这条时间线之外，**另做一条 180 秒的对齐标记片**，专门测漂移：

- 每 15 秒插一个标记：视频侧 1 帧纯白（其余为正常画面），音频侧同一时刻 40ms 的 1kHz 正弦。
- 标记落在 0/15/30/45/60/…/165 秒，共 12 个。
- 这条片子的分段结构与 ct_shiti 完全一致（22 段、同样的段边界），
  这样测出来的漂移才代表 ct_shiti 的漂移。

分析：

```bash
# 视频侧：找白帧（YAVG 突变）
ffmpeg -i rec.mp4 -vf "signalstats,metadata=print:key=lavfi.signalstats.YAVG" -f null - 2> y.log
# 音频侧：找 1kHz 能量峰
ffmpeg -i rec.mp4 -af "bandpass=f=1000:width_type=h:w=50,astats=metadata=1:reset=1,ametadata=print:key=lavfi.astats.Overall.RMS_level" -f null - 2> a.log
```

**漂移 = 音频峰时刻 − 白帧时刻**（正数为音频滞后）。逐个标记算，得到漂移随时间的曲线。

### 2.3 测什么

| 指标 | 定义（必须按这个定义采） |
|---|---|
| **切换间隙** | 上一段最后一帧上屏 → 下一段第一帧上屏。**逐帧从录屏判**，60fps 下 1 帧 = 16.7ms |
| **黑场时长** | 该间隙内实际显示黑帧的连续时长。**黑帧定义**：帧亮度 YAVG < 16（0–255 标度）且该亮度覆盖画面 ≥ 90% |
| **累计音画漂移** | 见 §2.2。分别报告 **45 秒**（方案判据点）与 **163 秒**（ct_shiti 实际片长）两个值，外加逐 15 秒曲线 |
| **首帧起播** | 用户点「播放」→ 第一段第一个非黑非占位帧上屏。t0 从录屏里按钮按下态那一帧取，不用埋点 |
| **掉帧率** | 整条连播的实际帧数 / 应有帧数。不是判据，但掉帧率高会让间隙数据失真，必须报告 |
| **内存与崩溃** | 连播 3 遍后是否 OOM/白屏/被系统回收。出现即整格判不通过，不看其他指标 |

### 2.4 通过线（在方案 §11.0 基础上补 max 线与黑场定义）

判定只看 **A-low 与 I-old 两台，M 网络档，冷缓存**。两台都过才算过。

| 指标 | 方案 §11.0 原线 | 本协议的可判定版 |
|---|---|---|
| 切换间隙 | ≤ 150ms | **P95 ≤ 150ms 且 max ≤ 400ms** |
| 无明显黑场 | 定性 | **黑场 P95 ≤ 33ms（2 帧）且 max ≤ 100ms** |
| 45 秒累计漂移 | ≤ 200ms | 不变，**并补 §2.5 的 163 秒线** |
| 首帧起播 | ≤ 1.5s | **P95 ≤ 1.5s 且 max ≤ 3.0s** |
| 崩溃 / OOM | 未写 | **0 次**，出现即不通过 |

为什么补 max：P95 允许 5% 的样本超线。21 个间隙的片子里，5% 就是**每条片子平均超一次**。
用户不看 P95，用户看见的就是那一次。max 线是防止「统计上过了、体感上没过」。

### 2.5 ⚠️ 修订建议：45 秒这条线本身有问题

**方案 §11.0 的「45 秒累计漂移 ≤ 200ms」是按 45 秒带货片写的，但 P0-a 唯一存在的模板是 163 秒的 `ct_shiti`。**

漂移在 `setTimeout` 驱动的实现里近似线性累积。45 秒 200ms 线性外推到 163 秒约是 **725ms**——
远超任何口型同步容忍度。也就是说**闸门 A 可以按现判据通过，而产品在真实模板上仍然对不上口型**。

广播行业常用的可察觉阈值（ITU-R BT.1359 口径，**用前需复核**）约为音频超前 45ms / 滞后 125ms。

建议判据改为：

| 补充判据 | 值 | 理由 |
|---|---|---|
| 163 秒累计漂移 | ≤ 400ms | 覆盖真实片长；线性累积下等价于 45 秒 ≈ 110ms，比原线严 |
| 任意 15 秒滑窗内漂移 | ≤ 125ms | 用户判断口型是局部判断，不是看总账；这条才是「口播对不对得上」 |

**这是对方案判据的修订，需要拍板后再改方案 §11.0 和 §5.5。** 本文先记录，不擅改。

### 2.6 不通过怎么办

方案 §5.5 已写死收敛形态，不在这里重议：第一档降级为静音顺序核对（现状能力），
第二档代理片扶正为默认主预览，§3.2 的「手机立即播放」改写为「约 N 秒后可看」。

**但报告必须额外回答一件事**：那个 N 是多少。它直接来自闸门 B 的单条墙钟时间，
所以两道闸门的报告要一起看，不能只跑 A。

### 2.7 报告必须回填到哪

- 方案 §5.5「第一档」小节：把实测三个数写进去，删掉「候选默认档，待闸门 A」的括号；
- 方案 §11.0 闸门 A 行：改为「已通过 / 未通过 + 日期 + 报告链接」；

- 若不通过，同步改 §3.2、§3.5，并把原型 `ProxyFallback.dc.html` 从「降级形态」提为默认形态。

## 3. 闸门 B：代理片成本与容量

### 3.1 先记录基线，否则数字没有意义

| 必须记录 | 说明 |
|---|---|
| CPU 型号、物理核数、超线程 | 「并发 4」在 4 核和 16 核上不是一回事 |
| 内存、磁盘类型（NVMe / SATA / 网络盘） | ffmpeg 是 IO 敏感的 |
| 是否与其他任务共机 | 与军师石榴生产链共机的话，闸门数据不能当独占容量用 |
| ffmpeg 版本与编译选项（`ffmpeg -version` 全文） | 有无 x264 汇编优化差一倍 |
| 输入素材集 | 与闸门 A 用同一组，保证两边可对照 |

### 3.2 必须产出的四个数（方案 §5.5 原文要求）

| # | 数 | 怎么测 |
|---|---|---|
| 1 | 45 秒 360p 代理单条墙钟 | 独占跑 N = 20 次，报 P50 / P95 / max |
| 2 | 同机并发上限 | 并发 1/2/4/8/12 各跑 N = 10，取**仍满足单条 P95 ≤ 60s 的最大并发**。同时记录 CPU 利用率与 1 分钟 load |
| 3 | 单项目单日代理次数上限 | 见 §3.4，这是产品口径不是实测值 |
| 4 | 缓存命中率假设 | 见 §3.5，**必须来自实测的修改行为样本，不能拍脑袋** |

同时必须记录一个方案 §5.5 点名的风险项：

> **`concat -c copy` 快路径有没有退化为全片重编码。** 每次跑测记录是否走了 copy 路径。
> 退化率高的话，第 1、2 个数全部作废重测——因为真实项目里的素材流参数就是不一致的。

**测试素材必须故意不一致**：混入不同分辨率、帧率（25/30/60）、编码档位、有无音轨的素材，
这才是真实用户上传的样子。全用规整素材测出来的墙钟时间没有参考价值。

### 3.3 163 秒也要测

同 §2.5 的理由：45 秒是带货片的长度，`ct_shiti` 是 163 秒。
**第 1、2 个数必须在 45 秒和 163 秒两个长度上各测一遍**，报告分列。
若 163 秒的 P95 超过 60s，代理片就不能承诺「自动升级」，
必须按方案 §5.5「改为用户主动点更新预览」的收敛形态处理。

### 3.4 单项目单日上限怎么定

这是产品决策，不是实测值，但要有推导：

```
单项目单日上限 = min(
  成本上限 / 单条代理成本,        ← 财务给单片预览成本上限
  同机并发上限 × 86400 / 单条墙钟 / 预期并发项目数   ← 容量上限
)
```

报告给出这个式子的三个输入的实测/给定值和算出来的数，**由谁签字定这个数要写清楚**。

### 3.5 缓存命中率假设：不许拍脑袋

`timelineHash` 缓存有没有用，取决于用户改东西的分布。要有样本：

- 从原型可点击版或 A 装置的用户测试里，采 **N ≥ 20 个真实项目**的修改序列；
- 每次修改按方案 §5.5 的 L1/L2/L3 分层打标（L1 结构 / L2 音频 / L3 样式）；
- 命中率 = 不触发代理全量重做的修改数 / 总修改数。

**L3 若不能独立重做，L3 修改也计入未命中**——这正是下一节要测的。

### 3.6 L3 独立重做 spike（方案 §5.5 明确要求「一并给结论」）

对照两条路径，同一条 45 秒代理片、只改字幕文本：

```bash
# 路径 A：全量重做（现状）
ffmpeg -i in.mp4 ... -vf "drawtext=..." -c:v libx264 out_full.mp4

# 路径 B：overlay 二次合成（只重做样式层）
ffmpeg -i base_no_subs.mp4 -vf "ass=subs.ass" -c:v libx264 -c:a copy out_overlay.mp4
```

**判定线：路径 B 墙钟 ≤ 路径 A 的 1/3，才算「L3 可独立重做」。**
差距小于 3 倍就没有分层的价值，多一套代码路径反而更贵。

结论直接决定一句界面文案能不能说：方案 §5.5 已经写死——
**L3 独立重做没落地之前，界面上只能承诺「手机层立即刷新、代理层稍后更新」，不能承诺样式修改即时刷新代理。**

### 3.7 报告回填

- 方案 §5.5「第二档」小节：四个数 + `concat` 退化率 + L3 结论；
- 方案 §5.5 的 `timelineHash` 三层表：L3 行的「否则退化为全量」改成确定结论；
- 方案 §11.0 闸门 B 行：通过/不通过 + 日期 + 报告链接；
- P0-a 的「单片成本表」条目：代理片这一项的成本来自这里。

## 4. P0-a 出口判据的可验证版

方案 §11.0 P0-a 的五条出口判据现在**没有一条能签字**——没有口径、样本量、证据来源和通过比例。
下面给可验证版。**这是提案，需要拍板后回填方案正文。**

### 判据 1 · 零资产新用户 10 分钟完成首条成片

| 项 | 口径 |
|---|---|
| 模板 | 固定 `ct_shiti`。换模板结论作废 |
| 「零资产」 | 无数字人、无声音、无素材、无商品的新账号，走公共数字人兜底（§P0-a 已列） |
| 计时起点 | 用户在首页点「用这套拍」的埋点时刻 |
| 计时终点 | 成片在作品页**可播放**的时刻（不是任务提交成功，不是进度 100%） |
| **含不含等待** | **含全部系统等待**：脚本生成、TTS、代理预览、数字人生成、总装、上传。这是产品承诺，不是工程耗时 |
| 扣除项 | 只扣除用户离开小程序的时间，按 `onHide`/`onShow` 事件对扣；单次离开 > 60s 的样本单独标注 |
| 样本 | **N = 10 名真实用户**，未看过演示，只给一句话任务（例：「给你自己的店做一条」），全程不指导 |
| 通过线 | **P50 ≤ 10:00 且 P90 ≤ 15:00**（N=10 时 P90 即第 9 名） |
| 证据 | 埋点时间戳 + 全程录屏，逐个样本可追 |

只写 P50 会出现「一半人 6 分钟、一半人卡死」也算过。P90 那条线是防这个的。

### 判据 2 · 扣费前看得到准确的字幕/音乐/裁剪/拼接/时长，且清楚哪几秒是示意

拆成两个可比对的集合：

**(a) 确定性字段逐条比对**（预览 vs 最终成片）：

| 字段 | 容差 |
|---|---|
| 每段字幕文本 | 完全一致 |
| 每句字幕时间窗 | ±100ms |
| 每段 `inSec`/`outSec` | ±100ms |
| 段顺序 | 完全一致 |
| BGM 曲目与音量 | 完全一致 |
| 总时长 | ±200ms |

**(b) 示意披露集合**：预览页声明为「待生成」的秒数区间集合，
必须与成片中实际由生成产生的秒数区间集合**完全相等**。多报或少报都算不通过。

- 样本：**N = 20 条项目**，其中 ≥ 5 条含用户主动先行生成某段的情况；
- 通过线：**0 例外**。这条是知情权，不能按比例过。
- 证据：预览时固化的 `PreviewRender` 快照 + 成片的实际时间线，两份 JSON 机器比对，比对脚本入库。

### 判据 3 · 已生成片段零重复生产

**证据口径：双证据，两个都要，缺一不算。**

| 证据 | 内容 | 判定 |
|---|---|---|
| (a) 供应商任务号 | `PreparedClip.vendorTaskId` | 同一个 `PreparedClip.id` 出现两个不同 `vendorTaskId` = 重复生产 |
| (b) 存储对象 | 对象 key + 内容 `sha256` | 成片消费的 key 与预览时固化的 key 相同，且 sha256 一致 |

只有 (a) 挡不住「供应商任务复用了但我们又下载重编码了一遍」；
只有 (b) 挡不住「同样的内容但确实付了两次钱」。所以两个都要。

- **前置工程量**：`PreparedClip` 表要有 `vendorTaskId` 与 `contentSha256` 两列。
  **`shared/contracts.d.ts` 里 `PreparedClip` 目前 0 处**（已复核），整条契约是新建。
- 样本：N = 20 条含先行生成的项目；
- 通过线：**重复生产计数 = 0**；
- 证据：结算流水 + 供应商任务号 + 对象存储 key/hash 三方对账，脚本化，可重复跑。

### 判据 4 · 首发三套模板全部通过真实出片验收

| 项 | 口径 |
|---|---|
| 「真实用户素材」 | 素材拍摄于真实经营场所 / 真实在售商品，由用户本人或其员工拍摄。**明确排除**：官方摆拍、图库、AI 生成画面、其他品牌的宣传物料 |
| 样本 | 每套模板 ≥ 5 条成片，来自 ≥ 3 个不同经营主体 |
| 验收人 | 模板生产线责任人（§13.9 第 7 项，**待指派**）+ 1 名不在本项目里的人，各自独立判 |
| 判定单位 | 单条成片判「可以直接发布 / 不可以」，二选一，不打分 |
| 通过线 | 每套模板的 5 条里，**≥ 4 条被两名验收人同时判为「可以直接发布」** |

**这条现在无法开始，原因写在这里免得被当成执行问题**：

1. 三套模板里只有「为实体发声」（`ct_shiti`）存在；「企业宣传片」要新写，「短视频带货」走 mixcut 是另一套子系统；
2. 带货那套卡在 §13.9 第 10 项**明星肖像授权链条**——那是「这套模板能不能存在」的前提，不是上线前补的合规项；
3. 验收人是 §13.9 第 7 项，**待指派**。

### 判据 5 · 单片成本表可直接用于定价讨论

必须列的字段，每项给 **P50 与 P95**，按模板分列：

| 成本项 | 计量 | 来源标注 |
|---|---|---|
| 脚本 LLM | 输入/输出 token × 单价 | 实测 |
| TTS | 字符数 × 单价 | 实测 |
| 数字人 | 供应商计费分钟 × 单价 | 实测 + 合同价 |
| 机审 | 次数 × 单价 | 实测 |
| 代理预览 CPU | 核·秒 × 折算单价（**来自闸门 B**） | 实测 |
| 总装 CPU | 核·秒 × 折算单价 | 实测 |
| 存储 | GB·月 | 实测 |
| 流量 | GB × 单价 | 实测 |

- 每项必须标注 **实测 / 合同价 / 估算** 三选一；
- 通过线：三套模板各一张表，且**标为「估算」的项合计占总成本 ≤ 10%**。
  估算占比过高的成本表不能用来定价，只能用来吵架。

### 关于「结构明显不同」

交接说明 §5 提到这条判据「没有样本数和通过比例」。
**复核结果：这句话不在方案 §11.0 的五条出口判据里，也不在方案正文任何位置**（已全文 grep）。
它应该来自混剪带货模板的成片去重要求，属于第 3 套模板的范畴。

若要纳入，建议口径（**未采纳，待拍板**）：

- 同一模板 + 同一商品连出 N = 10 条，两两比对；
- 「结构不同」定义为：段序列的**片段来源 ID 序列**编辑距离 ≥ 总段数的 30%，
  或 BGM/转场/字幕样式组合不同；
- 通过线：10 条两两 45 对组合中，≥ 40 对判为不同。

在第 3 套模板存在之前，这条不进出口判据。
