# 军师隔离压测 V2 报告

**执行日期**：2026-07-27（测试机本地时区跨日至 2026-07-28）  
**代码版本**：`8378049`  
**测试机**：47.98.162.120，4 vCPU / 7.3 GiB RAM / 115 GiB 可用磁盘级别  
**结论性质**：仅适用于单 API 进程、同机 PostgreSQL、mock LLM、只读 API 的隔离环境；不是生产 SLA，也不是独立 RDS 或真实 LLM 容量结论。

## 1. 结论摘要

1. **基础数据集（1,000 用户 / 10,000 会话 / 300,000 消息）**下，T1（API 不设 CPU 配额、仍与 PostgreSQL 同机）在 **450 RPS 连续 5 分钟**稳定：135,001 请求、0 错误、P95 72.3ms。350 RPS 同样稳定（P95 18.9ms）。
2. **600 RPS 已越过边界**：约 31.6 秒内错误率 18.9%、P95 1.30s，过载闸主动返回快速 503；没有 OOM、没有 swap、没有 429。有效安全容量不应按 600 标注。
3. **10 倍数据（10,000 用户 / 100,000 会话 / 3,000,000 消息）下容量明显收缩**：450 RPS 错误 8.0%，350 RPS 也有 1.9% 错误，均被 1% 错误护栏在约 30 秒自动停止。尚未建立该数据量下的连续 5 分钟稳定上限；生产首档应按 **≤250 RPS/实例（只读路由预算）** 保守配置，并补测 200/250/300 RPS。
4. **限流与真实 IP 语义已验证**：同一匿名 IP 在阈值 5/min 时精确得到 5 个 200 + 3 个 429；20 个不同 IP 全部 200，审计日志记录了全部 20 个原始 `X-Forwarded-For`。
5. **真实 LLM 并发没有得出结论**：以固定 1 字符输入、`max_tokens=1` 的并发 1 探针两次均返回 401，usage=0 后立即停止；未扩并发，未产生可用 token 消耗样本。需为压测单独配置可撤销、限额的模型凭据后复测。
6. **测试机已恢复**：隔离 Compose 项目与精确命名卷 `junshi_lt_pgdata` 已删除；原有 AIStarEcosystem、MySQL、Nginx、Bossclub 服务均恢复为 active/healthy，80/443/3306/8090/18080/55432 监听已复核。

## 3. 结果

### 3.1 启动与 T0 对照

| 运行 ID | 拓扑 / 数据 | 时长 | 实际 RPS | 错误率 | P95 | 判定 |
|---|---|---:|---:|---:|---:|---|
| `v2-s0-t1-r2` | T1 / 基础数据 smoke | 1 分钟 | 5.0 | 0 | 11.2ms | 通过 |
| `v2-s0b-t0-450-r1` | T0：API 2.25 核、PG 1.5 核、网关 .25 核 / 基础数据 | 2 分钟 | 444.0 | 5.04% | 1.41s | 不通过 |

T0 的失败不用于标注服务容量：它说明旧 cgroup 配额下 450 RPS 与 V2 的生产鉴权、Redis 限流、过载闸组合不可比。失败时过载闸快速 503，而不是把整机拖成秒级排队。

### 3.2 T1 容量阶梯（基础数据）

| 运行 ID | 目标 / 实际 RPS | 时长 | 请求数 | 错误率 | P95 | 结论 |
|---|---:|---:|---:|---:|---:|---|
| `v2-t1-samehostpg-350-r1` | 350 / 350.0 | 5 分钟 | 105,001 | 0 | 18.9ms | 通过 |
| `v2-t1-samehostpg-450-r1` | 450 / 450.0 | 5 分钟 | 135,001 | 0 | 72.3ms | 通过 |
| `v2-t1-samehostpg-600-r1` | 600 / 593.0 | 护栏约 31.6 秒停止 | 18,738 | 18.89% | 1.30s | 不通过，主动 503 |

600 RPS 时累计观察到 3,542 次过载闸拒绝，429 为 0。它证明“过载快速失败”有效，但不能把 600 RPS 当作容量；**基础数据集的实测稳定点是 450 RPS，建议上线预算最多取其 50%–60%（225–270 RPS/实例）**，给真实写入、LLM、报告渲染和流量突刺留余量。

### 3.3 10 倍数据集

数据生成完成并复核：10,000 用户、100,000 会话、3,000,000 消息；磁盘从约 29 GiB 占用升至约 31 GiB。

| 运行 ID | 目标 / 实际 RPS | 停止原因 | 请求数 | 错误率 | P95 | 判定 |
|---|---:|---|---:|---:|---:|---|
| `v2-s1b-10x-t1-450-r1` | 450 / 449.8 | 错误率 >1% 自动停止 | 14,239 | 8.01% | 41.1ms | 不通过（503） |
| `v2-s1b-10x-t1-350-r1` | 350 / 350.0 | 错误率 >1% 自动停止 | 11,105 | 1.90% | 20.8ms | 不通过（503） |

P95 仍低的原因是被拒绝请求以极短 503 返回；因此不能只看延迟分位数，必须同时看错误率和过载计数。后续应在 200、250、300 RPS 补齐连续 5 分钟阶梯，并按各接口端点拆分结果。

### 3.4 资源水位

| 运行 | 最低可用内存 | swap | API RSS 峰值 | 事件循环 P95 峰值 | PG 连接峰值 / 活跃峰值 |
|---|---:|---:|---:|---:|---:|
| T1 350 | 5.55 GiB | 0 | 204.7 MiB | 11.0ms | 87 / 4 |
| T1 450 | 5.32 GiB | 0 | 289.2 MiB | 11.6ms | 87 / 4 |
| T1 600 | 5.21 GiB | 0 | 370.6 MiB | 12.0ms | 86 / 7 |

结论：本轮边界不是内存或 swap，而是应用在途请求/连接池/同机数据库组合的吞吐拐点。Prisma 连接池在运行后保持约 80 个 open、活跃查询却仅为个位数；迁到 RDS 前后都应把每 API 实例的 `connection_limit` 重新校准到 20–30 起步，并用连接池代理或 RDS 代理控制横向扩容后的总连接数。`pg_stat_statements` 未启用，无法给出单 SQL Top-N；这是下轮观测缺口。

### 3.5 S2 限流、可信代理与审计

隔离环境临时设置 `LT_RATE_LIMIT_MAX=5` 与 `LT_TRUST_PROXY=172.26.0.0/16`（Compose edge 网关回源网段；没有使用不安全的 `true`）。每个子项前清空隔离 Redis。

| 运行 ID | 断言 | 实测 | 判定 |
|---|---|---|---|
| `v2-s2-single-ip-r2` | 同 IP 8 次：5 个 200、3 个 429 | allowed=5、429=3、unexpected=0 | 通过 |
| `v2-s2-multi-ip-r1` | 20 个不同 IP：均不受其他 IP 连带影响 | allowed=20、429=0、审计记录 20 条/20 个不同 IP | 通过 |

生产上 `TRUST_PROXY` 必须只填入口回源网段或可信跳数，不能把客户端 XFF 无条件信任；生产 Nginx 的 loopback 拓扑继续使用默认 `loopback` 即可。

### 3.6 最小 LLM 探针

| 运行 ID | 并发 × 请求 | 输入/输出限制 | 结果 | token 观测 |
|---|---:|---|---|---:|
| `v2-llm-c1-r1` | 1 × 1 | `"1"` / `max_tokens=1` | 非 2xx | 0 |
| `v2-llm-c1-r2` | 1 × 1 | 同上 | 401 | 0 |

执行规则是单响应总 token >200 或非 2xx 即停止；因此没有扩大到 c2/c4/c8，也没有得到并发容量。下一次使用**专用、可撤销、带日限额**的 QNAIGC/目标供应商 key，按 c1 → c2 → c4 → c8，每档 1 次请求推进；总调用上限 15 次、每响应 200 token 硬闸，并将供应商账单用量与 k6 usage 对账后才可给并发结论。

## 4. 部署与优化建议

### 立即执行

1. **保持 `MAX_IN_FLIGHT` 过载闸，不要为了“跑高 RPS”调大或关闭。** 600 RPS 的快速 503 是正确的隔离行为；入口层应向客户端返回可重试语义和退避策略。
2. **数据库迁 RDS PostgreSQL 是扩容前置。** 本次 T1 的 PG 与 API 共机，450 RPS 不能外推为生产多机容量；RDS 可提供备份/PITR，消除单机数据库故障域。
3. **先做 scheduler 选主/独立 worker，再加第二个 API 进程或实例。** 当前 scheduler 多进程会重复任务，不能用横向扩容掩盖这一前置缺口。
4. **报告 PDF 从 API 进程拆出。** 本轮不含 Puppeteer 渲染，真实出报告会侵蚀只读容量。
5. **补齐 SQL 观测。** RDS 侧开启慢 SQL/性能洞察；隔离栈在可接受时启用 `pg_stat_statements`，按端点记录查询和行数。

### 生产分层建议（先按实际并发、LLM RPM/TPM 与数据量校准）

| 阶段 | 推荐资源 | 适用边界 | 关键要求 |
|---|---|---|---|
| 验证/早期生产 | 1 × ECS 4C8G API，RDS PostgreSQL 2C4G，Redis 1 GiB，ESSD 100 GiB | 低于约 20 个活跃并发、以产品验证为主 | 单 AZ 可接受但必须 RDS 备份；API 只读预算按 200–250 RPS/实例看待 |
| 稳定增长 | 2 × ECS 4C8G API + ALB，RDS PostgreSQL 2C8G（高可用），Redis 2 GiB，独立 scheduler/worker 2C4G | 20–100 活跃并发或需容灾 | 先落选主；每实例 DB 池 20–30；发布滚动、告警、备份恢复演练 |
| 规模化 | 3 × ECS 8C16G API + ALB，RDS PostgreSQL 4C16G/只读与代理按压测决定，Redis 4–8 GiB，独立队列/worker/PDF worker | 100+ 活跃并发、报告任务或 LLM 任务显著 | 端点池、模型限流、队列长度、DB 连接与成本告警均需接入可观测平台 |

以上“活跃并发”不能由本次只读 RPS 直接换算；真实聊天的模型延迟、输出 token、上传/报告比例决定最终容量。上线前按真实访问分布再做混合压测。

### 5.3 LLM 成本与 QNAIGC 定价核验

七牛云官方文档确认模型服务提供**按 token 计费**和**资源包**两种方式，公式为：

`月成本 = 输入 token / 1,000,000 × 输入单价 + 输出 token / 1,000,000 × 输出单价`

详见 [QNAIGC 官方计费 FAQ](https://apidocs.qnaigc.com/7926450m0) 与 [服务主页](https://apidocs.qnaigc.com/)。公开文档没有可直接用于本报告的、按具体模型列出的固定单价表；因此不能把第三方或旧截图价格当作采购价。采购时在 QNAIGC 控制台针对目标模型导出“按量”和“资源包”两档报价，再按以下三个负载档做预算：

| 档位 | 需向供应商确认的量 | 成本控制 |
|---|---|---|
| 低 | 日会话数、平均输入/输出 token、缓存命中 | 单用户日额度 + `max_tokens` + 月预算告警 |
| 中 | 高峰 RPM、TPM、429 策略 | 主/辅模型分层、全局并发闸、队列超时 503 |
| 高 | 多账号/端点池配额、缓存与资源包折扣 | 端点池、共享冷却、供应商账单与内部 token 台账日对账 |

## 8. LLM 闸门补测（2026-07-28，零 Token）

此前“真实 LLM 最小探针”因测试环境的 OpenAI 兼容凭据返回 401 而按护栏停止；该凭据不应修补、猜测或从生产机复制。本次改为在同一台隔离机、同一套 mock API 中验证**服务自身的 LLM 并发闸与 429 冷却**：`AI_MOCK_LATENCY_MS=3000`、抖动 `0–500ms`、主车道常态 8 / 突发 12、队列超时 15 秒。mock 现在只在显式开启上述延迟时占用真实 `llmGate` 槽位，因而没有外部调用和 Token 消耗。

| 运行 ID | 并发 × 请求 | 成功 / 拒绝 / 超时 | 请求耗时 P95 | 最大排队 / 最长等待 | 判定 |
|---|---:|---:|---:|---:|---|
| `s5-queue-v8` | 8 × 8 | 8 / 0 / 0 | 3.68s | 0 / 0s | 通过；常态并发稳定 |
| `s5-queue-v12` | 12 × 12 | 12 / 0 / 0 | 3.59s | 0 / 0s | 通过；突发额度稳定 |
| `s5-queue-v20` | 20 × 20 | 20 / 0 / 0 | 6.57s | 8 / 3.14s | 通过；超出突发额度进入队列 |
| `s5-queue-v40` | 40 × 40 | 40 / 0 / 0 | 13.16s | 28 / 9.64s | 通过；未越过 15 秒排队超时护栏 |

确定性 429 测试将 `AI_MOCK_429_FIRST_N=1`：首个请求在 3.49 秒后按预期返回 429；指标随后记录 `upstream_429_total=1`、`cooldowns_total=1`，紧接的恢复请求先排队 3.30 秒、总耗时 6.78 秒并成功，证明冷却与恢复路径实际生效。首个注入请求的 `http_req_failed=1` 是有意的上游错误，不是压测失败。

**可得结论**：本服务可安全承接至少 40 个同时到达的、约 3 秒上游调用，超额请求按队列而非放大上游压力；这只是本地闸门容量和队列行为，不等同于供应商模型并发配额。真实 QNAIGC/OpenAI 并发仍需专用、可撤销、日限额的测试 key 才能测定；现有测试 key 401、Token 用量为 0，不能据此给出供应商容量。

新增工件：`loadtest/k6-llm-queue.js`、每档 `loadtest/results/s5-queue-v*.json` 及对应 `*-monitor/llm.csv`、`s5-429-{trigger,recovery}.json`。补测完成后已再次删除隔离 Compose 网络/容器/`junshi_lt_pgdata`，并复核原测试机 Nginx、MySQL、AIStarEcosystem 与 Bossclub 服务恢复 active/healthy，站点 loopback 探测返回成功。
