## 1. P0-0【新增·最高优先级】生产全局限流会把吞吐锁死在约 5 RPS，压测结构性测不到

**这是本次核对最重要的一条：报告的 450 RPS 在当前生产配置下根本达不到，且和机器规格无关。**

证据链：

1. `server/src/app.ts:51` 建实例时是 `Fastify({ logger })`，**没有 `trustProxy`**。Fastify 因此用 socket 对端地址做
   `req.ip`，`X-Real-IP` / `X-Forwarded-For`（`deploy/nginx.conf.example:20-21` 确实设了）被完全忽略。
2. `server/src/app.ts:74-80` 全局注册 `@fastify/rate-limit`，`max: 300`、`timeWindow: '1 minute'`，未传
   `keyGenerator`。该插件 v10.3.0 的默认键是 `req.ip`（`node_modules/@fastify/rate-limit/index.js:29`）。
3. 生产 Nginx 从 `127.0.0.1` 反代到 Node（`deploy/nginx.conf.example:17`）。于是**所有用户的 `req.ip` 都是
   `127.0.0.1`，共用同一个 300/min 的桶** → 全站合计约 **5 RPS**，超出即 429。
4. 压测栈 `loadtest/docker-compose.yml:32` 设 `NODE_ENV: test`，`isAiTestMode()`（`server/src/env.ts:13-16`）返回
   true，`app.ts:73` 的 `if (!isAiTestMode())` 直接**跳过了限流插件的注册**。所以 450 RPS 这一档从头到尾没有
   经过限流层——这个缺陷压测**结构上不可能发现**。

动作：

- `buildApp` 传 `trustProxy`，且**不要用 `true`**（会无条件信任任意来源的 XFF，Node 端口一旦可达即可伪造 IP）。
  用跳数或网段：本机 Nginx 反代用 `trustProxy: 1`；上 ALB 后改成 ALB 的回源网段。
- 复核全局阈值。300/min/IP 对**单个自然人**是合理的；修好 `trustProxy` 后它才真正是「每 IP」。但小程序用户大量
  出自同一运营商 NAT 出口，建议：全局桶放宽到按 IP 1000–2000/min 只作防扫描兜底，**真正的成本闸按 userId 收紧**
  （成本型路由已有 route-level 配置的先例，见 `server/src/routes/auth.ts:208,247`）。
- 限流 store 换 Redis（见 P0-4），否则双实例后每实例各算各的，实际阈值翻倍。
- **复测必须带上限流层**：压测栈不能再用 `NODE_ENV=test` 跑容量档（见第 6 节）。

验收：Nginx 反代后 `req.ip` 等于真实客户端 IP（打日志或 `/api/health` 回显验证）；450 RPS 复测 429 数为 0。

## 2. P0 · 复测前必须完成

### P0-1【报告项】把压测网关的调优回流到生产 Nginx 模板

报告 800 RPS 档 46.03% 失败的直接原因是 Alpine 默认 `worker_connections=1024` 先耗尽。隔离栈
`loadtest/nginx.conf` 已经调好，但**这些设置一条都没有回流到 `deploy/nginx.conf.example`**——生产现在跑的
就是那个会在 800 RPS 崩掉的默认配置，而且更差：没有 `upstream` 块，`proxy_pass` 直连
`http://127.0.0.1:4000`，既无 `keepalive` 也无 `Connection ""`，**每个请求都新建一条到 Node 的 TCP**。

需要补进 `deploy/nginx.conf.example` 的（对照 `loadtest/nginx.conf`）：

| 项 | 压测栈值 | 生产模板现状 |
|---|---|---|
| `worker_connections` | 8192 | 未设（默认 512/1024） |
| `worker_rlimit_nofile` | 65535 | 未设 |
| `upstream` + `keepalive` | 512 | 无 upstream 块 |
| `proxy_set_header Connection ""` | 有 | 无（keepalive 不生效的前提条件） |
| `proxy_http_version 1.1` | 有 | 有 ✅ |

顺带一并处理：

- 【新增】SSE 补 `X-Accel-Buffering: no`。全仓 grep 零命中；生产模板靠 `proxy_buffering off` 兜住，但换 ALB 或
  中间再加一层就会憋断流。这是「上 ALB」这条 P0 的前置条件，不是可选项。
- 【新增】`limit_req` / `limit_conn` 过载保护，见 P0-5。

验收：同机复跑 800 RPS，失败不再来自网关连接耗尽；`ss -s` 观察到 Node 上游连接被复用而非线性增长。

### P0-2【报告项 + 口径修正】LLM 并发闸：代码里目前完全不存在，且只做 semaphore 不够

现状核对：`server/src` 全量 grep `semaphore|concurren|p-limit|bullmq|inflight` **零命中**。已有的只是
provider 层的单次调用 timeout 与 SDK 重试（`server/src/llm/providers/claude.ts:38,104,160,184,210,264`、
`openai.ts:46-114`）。**全局并发上限、队列、429 感知退避，三样都是从零开始建。**

口径修正——报告 §5 有一条观察比 semaphore=8 这个数字更重要：

> 20 并发触发 429 后，**紧接着的 12 并发复测 48/48 全部 429**；等窗口恢复后 8 并发 80/80 成功。

这说明上游是**滚动时间窗限额**，不是纯瞬时并发限额。只装一个 `semaphore=8` 挡不住它——8 条长请求持续跑满，
一样会在窗口维度撞线。所以要同时做三件事：

1. **并发闸**：全局 semaphore=8，burst=12（报告值，直接采用）。
2. **速率窗口闸**：单位时间请求数 / Token 数的滑动窗口配额。阈值本轮没测出来，先按保守值上线并用真实
   429 率反推校准。
3. **429 处理**：优先读 `Retry-After`；无该头则指数退避 + **整窗冷却**（一旦 429，全局闸临时降档而不是让每条
   请求各自重试——`claude.ts:38` 现在的 `maxRetries: 2` 在限额窗口里只会放大打击）。

配套：Redis 分布式队列（跨实例才有意义）、队列可见 / 可取消 / 可超时、等待 >15s 主动降级提示。

验收：20+ 并发不直打供应商；注入连续 429 后系统自动降档并在窗口恢复后回升；队列深度、等待时长、429 率有
指标可读。

### P0-3【口径修正】Prisma 连接池：`80/实例` 是压测栈的值，生产是「没设」

报告写「从 80/实例降至 10–20」。核对后：

- `connection_limit=80&pool_timeout=10` 只出现在 `loadtest/docker-compose.yml:35`，是**压测栈专有**。
- 生产 `server/src/db.ts` 是裸 `new PrismaClient()`；`deploy/docker-compose.yml:38` 的 `DATABASE_URL` 不带
  任何池参数 → Prisma 走默认 `num_cpus × 2 + 1`，4C 机器上是 9。

所以生产上真正的问题不是「80 太大」，而是**这个值是隐式的、跟着容器看到的 CPU 数漂移**：同一镜像放到 8C 节点
变 17，放到 ACK 2C Pod 变 5，扩容时连接总量不可预算。动作因此改写为：

- **显式**在 `DATABASE_URL` 里设 `connection_limit`（建议 10–20/实例）+ `pool_timeout`，不再依赖默认推导。
- 按 RDS `max_connections` 反推每实例配额：`每实例上限 × 最大实例数 ≤ max_connections × 65%`，剩余留给
  worker、迁移和运维连接。
- 压测数据支持收紧：450 RPS 稳态下**总连接峰值 86，而 active 峰值只有 4、idle-in-transaction 峰值 4**——
  80 的池子实际用了不到 5%。

验收：横向扩到 6 实例，DB 连接总数仍在预算 60–70% 以内；复测 450 RPS 不出现 `pool_timeout` 报错。

### P0-4【口径修正】"单进程到顶"这个依据不成立；先修障碍、先搬 PG，多进程收益需实测

报告 §1 写「Node 单进程在约 2.25 核处到顶；横向扩展比继续堆内存更有效」，依据是 API CPU 峰值 229.65%。
**这个因果链没有数据支撑**：`loadtest/docker-compose.yml:86` 明确设了 `cpus: 2.25`，229.65% 就是**容器
cgroup 配额跑满**，不是 Node 的架构上限。三个容器 API 2.25 + PG 1.5 + Nginx 0.25 = 恰好 4.0 核，是人为切分。

后果有两个：

1. `450 RPS` 是"2.25 核 API"的容量，不是"4 核机器"的容量；
2. **"多进程能带来多少收益"这个问题，上一轮一次都没测过。** 单进程的真实天花板可能高于 2.25 核
   （Node 主线程约 1 核跑 JS，Prisma 的 Rust 查询引擎有独立 tokio 线程池，合计超过 2.25 核完全正常），
   也可能低于。当前数据无法区分。

所以本条**不能按"多进程一定有大收益"来排期**。多进程仍然值得做（`deploy/junshi-api.service:17` 现在是
`ExecStart=/usr/bin/node dist/index.js`，全仓无 cluster / pm2 / `WEB_CONCURRENCY`，就是一个进程），但它的
优先级要等 V2 压测的 T1 vs T2 对照实验出结果再定，见 `docs/[OPUS5]LOADTEST_PLAN_V2_2026-07-26.md` S1。

不受这条影响、可以照做的是**顺序**：本轮 API、PG、Nginx 跑在同一台 4C 机器上，直接在同机加进程一定会和
PG 抢核。所以无论多进程收益多大，正确顺序都是：

1. **PG 迁 RDS**（同时拿到备份 / PITR，`docs/[FABLE5]SCALE_ARCH_PLAN_2026-07-22.md` Phase 0 已列为头号动作）；
2. **同机 2–3 个 API 进程**（cluster 或多容器 + Nginx upstream 多 server）；
3. **双实例 + ALB**（为可用性和滚动发布，不只是为算力）。

但 2 和 3 都会踩同一批障碍。逐条核对 `SCALE_ARCH_PLAN` §1 的清单，当前状态：

| 障碍 | 现状 | 结论 |
|---|---|---|
| 优雅停机 | `server/src/index.ts:23-38` 已实现 SIGTERM → `stopScheduler` → `app.close()` → `$disconnect` | ✅ **已修**，报告「单实例下线无中断」的应用侧前提已具备，缺的只是 ALB 连接排空 + 健康检查接线 |
| 进程内定时器 | `server/src/services/scheduler.ts:27,51` 仍是每进程 `setInterval` 跑全量 job | ❌ **多进程/多实例会重复推送微信订阅消息、重复发一次性额度**。需 Redis 选主或独立单实例 cron worker + `(userId,scene,date)` 幂等唯一约束 |
| 限流 store | `@fastify/rate-limit` 用默认内存 store（`app.ts:74`） | ❌ 需换 Redis store（与 P0-0 同一处改动） |
| 进程内缓存 | `server/src/services/cache.ts` 已有 Redis 分支，`ioredis` 在 `optionalDependencies` 且已安装 | ⚠️ 代码就绪，**只差生产真的配上 `REDIS_URL`** |
| PG 连接池 | 见 P0-3 | ❌ |
| Puppeteer 进程内 | 见 P1-1 | ❌ |

健康检查【新增】：`server/src/routes/meta.ts:20-31` 已经是真 DB ping（`SELECT 1` + 2s 超时 → 503），可以直接给
ALB 用，比浅 `ok:true` 强。但压测里它占 5% 流量、且在限流 allowList 里；ALB 高频探活会**每次打一条 DB 查询**。
建议拆 `/health/live`（进程存活，不碰 DB）与 `/health/ready`（含 DB，结果 1s 内复用）。

### P0-5【新增】过载主动降级，而不是让请求排到客户端超时

报告 §3/§4 的失败形态是**排队 + 10s 超时**，不是进程崩溃：450→500 RPS，P95 从 39.6ms 放大到 6.23s。这类
悬崖靠扩容只能把位置往右推，推不掉——真正要补的是**过载时快速失败**，用少量 503 换住整体 P95：

- Nginx 层 `limit_req` + 有界 `burst` + `nodelay`，超出直接 503，不让请求在队列里熬到 10s。
- 应用层给在途请求数设上限，超过即拒（返回明确的「稍后重试」而非静默排队）。

验收：500 RPS 档下 P95 不再出现秒级放大；超出容量的部分表现为快速 503 而不是全体延迟劣化。

### 先纠三处错

| 系统提示词 17,232 字符 | **49,094 字符**——那 17,232 是仓库文件 `prompts/strat.v6.md`，生产库里的是它的 2.85 倍 |

| 「16 个注入块每轮全发」是 input 主因 | 账本块是零头。**系统提示词就是几乎全部输入** |

| kind | 调用 | 输入 token | 缓存命中 | 输出 token |
|---|---|---|---|---|
| **chat** | 580 | **16,445,560** | 1,735,595 | 457,406 |
| deliverable | 54 | 1,165,982 | 146,035 | 120,073 |
| aux | 400 | 143,888 | 0 | 21,183 |

chat 平均输入 **28,354 token**；已发布的 `AgentVersion` v4 是 49,094 字符 ≈ 27,000 token。
**系统提示词占单次输入的 95% 左右。**

规模很小：**近 10 天日均 13–104 次对话、3–9 个活跃用户**，离任何容量上限都很远。
所以 LLM 的「瓶颈」目前是**成本与配额结构**问题，不是吞吐问题。

### 真正的大头：提示词缓存 88% 没命中

```
580 次 chat 中 509 次（88%）cachedInput = 0
这 509 次白付了 13,740,038 个输入 token
```

**不是 TTL 的问题。** 同一用户相邻两次对话的间隔：71.6% 在 5 分钟内。收窄到只看窗口内的
415 次调用，命中率**仍然只有 15.2%**。

**也不是我们代码的问题。** `stable` 段里没有随时间变的值（`contextValues` 无日期类；
生产提示词只有一个 `{h,b}` 占位符，`fillPlaceholders` 基本是空操作），`buildSystemParts`
的稳定段在前、变化段在后，符合前缀缓存要求。

**指向网关。** 生产走 `https://api.qnaigc.com/bypass/anthropic`（七牛中转）。
最可能的原因是这类中转在一批上游账号间轮询，而 Anthropic 的提示词缓存**按账号隔离**——
A 账号写的缓存，下一次请求落到 B 账号就读不到，命中率 ≈ 1/账号池大小。15% 大致对应 7 个左右。
两个模型标签（`claude-opus-4-6` 17.5% / `dj-claude-4.6-opus` 9.4%）命中率都低、且呈零星脉冲，
都符合这个模式。**这是推断，看不到网关内部。**

### 成本（Anthropic 官方列表价）

Opus 4.6：input **$5.00/1M** · output **$25.00/1M** · 缓存写入 5m TTL **1.25× = $6.25/1M** ·
1h TTL 2× = $10.00/1M · 缓存读取 **0.1× = $0.50/1M**。

| kind | 缓存读 | 其余输入 | 输出 | 合计 |
|---|---|---|---|---|
| chat | $0.87 | $73.55 | $11.44 | **$85.85** |
| deliverable | $0.07 | $5.10 | $3.00 | $8.17 |
| aux | — | $0.72 | $0.53 | $1.25 |
| **总计** | | | | **≈ $95.28 / 30 天** |

> ⚠️ **系统内 `costMicros` 记的是 18.36，低估约 5.2 倍。** `data/modelPrices.ts` 的单价需要按官方价校准，
> 否则运营后台的「算力消耗」和成本告警都是错的。

**缓存修好能省多少**（按命中样本实测的可缓存前缀 25,076 token/次 × 509 次未命中）：

| 情景 | 成本 | 相对现状 |
|---|---|---|
| 现状（按全价 input 计） | $63.82 | — |
| 全部走缓存读（理想上限） | $6.38 | 省 $57.44 |
| **现实（85% 读 + 15% 写 5m TTL）** | **$17.48** | **省 $46.33 = 总账单的 49%** |

单位经济：**$0.164/次对话 → 约 $0.084/次**，接近腰斩。

两点保守说明：① `usageOf` 把 `cache_creation` 折进了 `inputTokens`，无法与新鲜输入分离，
所以现状那 $63.82 实际只会更高（写入是 1.25×），省的更多；② 当前绝对值不大，
但**线性放大**——用户涨 100 倍就是每月约 $9,500，其中约 $5,700 是纯浪费。

> ⚠️ **一个前提必须先确认**：以上省钱推算成立的前提是**七牛中转按 Anthropic 的缓存定价结构结算**
> （读 = 1/10 输入）。如果它只按统一 token 单价计费、不透传缓存折扣，那么修好缓存亲和性
> **省不到钱**——只能改善延迟和 TPM 压力。这条要和配额问题一起问七牛。

## 3. P1

### P1-1【报告项 + 口径修正】Puppeteer / 长任务移出 API 进程 —— 报告的 450 RPS 不含报告渲染

`server/src/services/reportPdf.ts:66-86` 是 API 进程内的 Puppeteer 单浏览器单例。本轮只读压测**完全没碰它**
（报告 §9 已声明未覆盖报告渲染）。这意味着 450 RPS 这个数字带一个隐藏折扣：生产上一旦并发出报告，Chromium 的
内存尖峰和 CPU 会直接和只读流量抢同一个进程的资源。

因此这条虽在报告里排 P1，但要加一个硬门槛：**在报告功能对外开放放量之前必须完成**，否则 350–400 RPS 的护栏
在有报告流量时不成立。

同批做掉：知识库确认入库 / 嵌入异步化、辅助抽取（当前 `void` fire-and-forget）入队并带重试与计量。

### P1-2【报告项】可观测性从零建，且必须和压测同口径

现状：无 `/metrics`（全仓无 prom-client / Prometheus），无 request-id 贯穿，无结构化错误上报。

报告要求「压测与线上告警使用同一套指标口径」，所以顺序是**先定指标口径，再接 SLS / ARMS / CloudMonitor**，
而不是反过来。最小指标集：RPS、P50/P95/P99、错误率、DB 连接数（total / active / idle-in-transaction）、
LLM 队列深度与等待时长、LLM 429 率、Token 消耗与日预算进度。

k6 侧同步：`loadtest/k6-readonly.js:54` 已经打了 `endpoint` / `run_id` tag，指标命名对齐它即可。
