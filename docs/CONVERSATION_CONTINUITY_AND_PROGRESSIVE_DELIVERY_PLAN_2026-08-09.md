## 1. 目标与非目标

### 1.1 目标

1. 用户隔天再次进入总军师时，军师仍然知道客户事实、关键决策和上次谈到哪里。
2. 长会话不因继承上下文而无限增加模型输入、延迟和费用。
3. 用户明确要求“帮我出报告”时仍然立即得到报告，不被复杂度判断拦截。
4. 军师推断出的事实不能未经用户确认就升级为客户事实。
5. 多图、复杂方案可以分批处理，但用户感知仍是一条连续、完整且由用户决定是否继续的交付链。
6. 每次上下文继承、报告路由和事实确认都有可审计来源与预算。

### 1.2 非目标

1. P0 不重做全部长期记忆系统。
2. P0 不迁移或重写历史消息。
3. P0 不要求用户重新描述企业背景。
4. 本方案不把“报告内容包含几个执行阶段”和“报告分几次生成”混为一件事。
5. 本方案不允许模型仅凭主观感觉决定任务复杂度或事实真伪。

## 2. 实施前基线与问题定位（2026-08-09）

本章的“当前”均指 2026-08-09 实施前代码快照，用于解释改造原因；实施后的真实口径以 §0.1、AGENTS.md 与代码为准。

### 2.1 24 小时新会话

当前问策终态会在冷启动时判断主线会话是否闲置超过 24 小时。满足“超过 24 小时且无未读消息”后，客户端不再续接旧会话，而是以无 `sessionId` 的方式开始新会话。

这会产生两个不同层面的问题：

- 视觉上是新会话；
- 数据上也创建了新 `Session`，旧 `SessionContextSnapshot` 不会自动继承，因此第一轮接近零会话上下文。

问题不在于旧会话太长，而在于摘要与旧 `Session` 绑定后没有跨会话交接。

### 2.2 长会话并不会整段进入模型

当前后端已有两层限制：

- 普通对话最多携带最近 16 条原文；报告轮只有在“判定为将产出成果、摘要已追平、摘要非空”三项同时成立时，才进一步收窄到 8 条（`DELIVERABLE_HISTORY_MESSAGES`）；
- 最近原文总字符预算为 12,000，单条另有 2,000 字符截断，相邻同角色消息会被合并，实际携带条数常少于 16；
- 用户明确追问过去内容时，才从更早 160 条中召回最多 6 条摘录，预算 4,500 字符；
- `SessionContextSnapshot` 按批次抽取事实、目标、约束、决策、行动项等结构化条目。

对应实现：

- `server/src/routes/sessions.ts`：`RECENT_HISTORY_MESSAGES`、`RECENT_HISTORY_CHAR_BUDGET`、`CARRYOVER_CHAR_BUDGET`
- `server/src/services/sessionDigest.ts`：增量摘要与来源消息校验

因此，取消 24 小时断链不等于把 220 条原文全部发送给模型。

### 2.3 现有摘要不能直接当跨会话最终交接包

当前摘要是追加式索引，上限约 400 条（软上限：撞顶检查在批前而非批后，单批最多 10 条，实际可冲到 409 条）：

- 新旧冲突事实都会保留；
- 既包含客户事实，也包含军师建议和历史行动项；
- 撞顶后停止继续抽取，尚未实现合并压缩；撞顶且游标后仍有新消息时 `caughtUp` 恒为 false（若没有待处理消息，当前代码会在撞顶检查前返回 true），调用方仍无法区分「尚未追平」与「已撞顶不再抽取」，会反复空转重试；
- 摘要属于单个 `Session`，新会话不会自动继承。

所以它适合做“有来源的历史索引”，但不适合不加处理地复制到每个新会话。

### 2.4 当前图片与报告机制

- 原生小程序每次选图最多 4 张；对话附件总数上限为 9。客户端「9」「4」与服务端「4」是三处独立字面量，没有共享常量。
- 服务端每条消息也只解析前 4 张图片，超出部分仅 `console.warn` 后静默丢弃，用户不会收到任何提示。
- 单张图片允许最大 10MB，服务端读取后以 base64 形式交给多模态模型，目前没有整批图片总字节预算——最坏情况 4 张 10MB 原图经 base64 膨胀后单请求约 53MB 图片载荷，无任何闸门。
- 对按需产出的智能体，后端通过明确的关键词规则识别“生成/输出/出一份/出报告/出方案”等要求并进入报告路径。同一正则在 `sessions.ts` 与 `generationRequest.ts` 各存一份字面量副本（后者未 import），`mock.ts` 另有第三套不同的正则；当前没有任何否定意图判断，“先别出报告”今天就会被误判进报告路径。
- 长期记忆目前会在对话后自动抽取并直接写入，数据模型没有 `pending/confirmed/rejected/superseded` 等事实确认状态；记忆条目只有粗粒度 `source`（conversation/document/deliverable_feedback），没有 `sourceMessageIds`，无法回溯到具体消息。
- 会话详情接口当前一次返回该 `Session` 的全部消息，小程序也一次性归一化并渲染全部历史；24 小时断链取消后，长期主线会把接口响应、`setData` 与 WXML 渲染压力持续放大，必须与 P0 同批补分页，而不能只治理模型上下文。

## 3. P0：取消零上下文新会话

### 3.1 推荐方案

闲置 24 小时后：

1. 继续使用最近一条总军师主线 `Session.id`；
2. 不再以空 `sessionId` 创建新会话；
3. 前端在消息流底部插入“新的一次问策 · YYYY-MM-DD”视觉分隔；
4. 分隔只表示新篇章，不代表模型上下文清零；
5. 有未读主动消息时仍沿用现有续接和已读逻辑；
6. 24 小时只在冷启动时决定是否显示新篇章，不在用户正在聊天时突然切换；
7. 服务端在首条新用户消息建单时，以“当前消息之前的最后一条真实消息时间”为准重新计算是否跨 24 小时，并把 `newChapter` 冻结进 GenerationJob 请求快照，不能只信客户端传值。冻结值仅供 trace 与可观测（§10 的 `newChapter/chapterGapHours`）使用；渲染真源始终是客户端按消息时间即时推导（见 §3.3），不得反过来实现成服务端驱动分隔。

### 3.2 为什么 P0 不需要临时重新压缩

新篇章第一轮直接复用：

- 原 `SessionContextSnapshot`；
- 最近 16 条受限原文；
- 当前用户档案与长期记忆；
- 明确回忆意图下的旧原文摘录。

不能在用户打开页面时额外发起一次“总结 220 条消息”的模型调用，因为这会增加首轮等待、费用和失败点。摘要应在平时对话结束后增量更新，打开会话只读取现成结果。

### 3.3 P0 视觉规则

- 新篇章分隔不创建一条假的用户或军师消息；
- 分隔不持久化：客户端按真实消息时间即时推导，换设备、清缓存后重算结果一致，不新增本地或服务端存储；
- 服务端已经返回 `SessionMessage.at`，但当前 `chat-core/behavior.js#normalizeMessage` 会丢掉它；批次 A 必须先保留 `at`，再计算分章；
- 已有消息流中只允许在**用户消息前**显示分隔：该用户消息与上一条真实消息相隔超过 24 小时即 `showChapterBefore=true`。不能对任意相邻消息套规则，否则一个延迟超过 24 小时才完成的军师报告会被误画成新篇章；
- 用户隔天打开但还没发送时，在消息流底部显示一个临时“新的一次问策”分隔；用户发出首条消息后，分隔自然归属到该用户消息；
- 分页加载更早消息时，要用前后两页边界消息的 `(at,id)` 重新判断分隔，不能在分页接缝重复或漏画；
- 分隔不进入报告、长期记忆或摘要抽取；
- 历史列表仍是一条总军师主线，避免 P0 同时改历史列表与会话模型；
- 未来如果需要历史列表展示多个视觉线程，再进入第 4 章的真实跨 `Session` 方案。

### 3.4 P0 回滚

实施阶段 A1 单独上线时，唯一回滚曾是恢复旧的 24 小时断链行为。当前批次 C 已同步完成，正式发布的逃生路径改为关闭 `conversation-continuity`：跨 24 小时创建新 `Session`，同时生成 `SessionHandoff`，因此视觉/数据可回退为独立会谈，但不能再回退成零上下文。

### 3.5 P0 连锁风险：摘要 400 条上限从理论问题变成必然问题

当前 24 小时断链客观上充当了摘要重置机制。P0 取消断链后主线 `Session` 永不切换，活跃用户的摘要必然撞上约 400 条软上限：之后新事实不再被抽取，且 `caughtUp` 恒为 false，trace 会把“撞顶”误报成“未追平”，误导排查（见 2.3）。

批次 A 虽不改数据库，但必须同步做两件事：

1. 增加撞顶监控告警，以条目数本身为告警信号（接近上限、已达上限），不能依赖 `caughtUp` 翻 false 才发现——现状撞顶但游标后暂无新消息时仍返回 true，撞顶状态完全不暴露，直到下一条新消息出现才变 false；
2. 把“摘要合并压缩”明确排期在批次 C 之前，不能等撞顶用户出现“军师突然记不住新事实”的隐性退化后再补。

### 3.6 P0 连锁风险：会话详情与端上渲染无限增长

当前 `GET /sessions/:id` 会按时间升序返回全部历史消息，小程序随后把全部消息一次放进 `setData` 并由 WXML 渲染。P0 让总军师主线不再自然换 `Session` 后，这条读取链会随使用时长无限增长，即使模型输入仍受 16 条/字符预算保护，端上也可能先出现接口响应过大、首屏变慢、滚动卡顿或 `setData` 压力。

批次 A 必须同步改为消息游标分页，不改数据库：

- `GET /sessions/:id` 默认只返回最近 80～100 条消息和 `hasMore`；
- 增加 `(createdAt,id)` 复合游标向上加载更早消息，避免同毫秒边界重复或漏项；
- `SessionDetail` 契约增加分页信息，先改 `shared/contracts.d.ts`；
- 小程序首次只渲染尾页，用户上拉时加载前一页，并保持当前阅读位置；
- 模型的 `loadConversationHistory` 继续直接从数据库按自身预算取数，不受端上分页影响；
- 发布前用至少 1,000 条消息、包含多份结构化报告和图片引用的会话验证首屏响应大小、耗时、滚动和继续加载。

### 3.7 P0 摘要状态：不能继续只用 `caughtUp: boolean`

当前普通聊天轮走纯读路径时会把 `caughtUp` 固定返回 false，即使快照实际已经覆盖旧历史；同时 false 还混合了批数用尽、抽取失败、冷却、预算超时、条目撞顶和归属异常。故 §12 不能直接以现有 `caughtUp=true` 作为普通聊天验收条件。

批次 A 应把内部结果和 trace 升级为可解释状态：

```ts
type DigestStatus =
  | 'caught_up'
  | 'pending'
  | 'capped'
  | 'cooldown'
  | 'failed'
  | 'unknown'

interface DigestCoverage {
  status: DigestStatus
  coveredThroughMessageId?: string
  coveredThroughAt?: string
  pendingMessagesBeforeCurrent: number
  items: number
  injectedChars: number
}
```

每个状态都必须有明确触发条件，不允许把任何状态当垃圾桶：

- `caught_up`：覆盖游标已达当前用户消息之前的最后一条历史消息；
- `pending`：仍有待消化消息（批数用尽、尚未追平）；
- `capped`：条目撞顶停止抽取——无论游标后是否还有新消息（现状撞顶且无待处理消息时返回 true，会掩盖撞顶）；
- `cooldown`：抽取连续失败进入熔断冷却期；
- `failed`：本轮抽取调用失败；同步预算超时不单独算 failed，超时后回落纯读并按读出的游标计算真实状态（通常为 `pending`）；
- `unknown`：读取快照本身失败或更新整体 reject（现状表现为 `digest === null` 而非 `caughtUp=false` 的那类场景），无法判定覆盖。

覆盖边界只计算“当前用户消息之前”的历史；本轮用户原文本来就会独立进入模型，不要求先被摘要消化。`readSessionDigest` 需要读出快照游标，并与当前消息之前的最后一条历史消息比较，不能再用纯读路径固定 false 代替真实状态。消费方也必须区分「有摘要但未追平」与「摘要读取失败（现状 `digest === null`）」两种情况，两者的历史窗收窄策略不同。

P0 不因摘要暂时 pending 阻塞用户回复：最近原文仍按 16 条兜底；但 `capped/failed` 必须被 trace 和监控明确暴露，不能伪装成已完整继承。

## 4. P1：真正的新 Session 与跨会话交接包

当产品需要在历史列表中把每次会谈展示成独立线程时，再创建真实新 `Session`，同时建立主线关系：

```text
ConversationLineage
└── Session A
    └── Session B（continuationOf=A）
        └── Session C（continuationOf=B）
```

建议增加：

- `Session.lineageId`：同一总军师主线标识；
- `Session.continuationOf`：直接来源会话；
- `SessionHandoff`：来源会话生成的交接快照；
- `handoffVersion`、`lastSourceMessageId`、`updatedAt`：增量更新和审计信息。

### 4.1 交接包内容

只保留当前有效的四类信息：

1. 客户已陈述或确认的事实；
2. 已形成的关键决策；
3. 当前目标、约束与红线；
4. 最近谈到哪里、待解决什么、下一步原计划做什么。

不应直接继承：

- 已被更正的旧事实；
- 军师未经确认的推断；
- 已完成且不再相关的行动项；
- 大段历史建议原文；
- 全部 400 条摘要条目。

### 4.2 上下文预算

建议先用字符预算落地，稳定后切换为 provider tokenizer 的 Token 预算：

| 上下文层 | 建议上限 |
|---|---:|
| 长期客户事实 | 2,000 字符 |
| 上一主线交接包 | 3,000～4,000 字符 |
| 当前线程最近原文 | 12,000 字符 |
| 明确回忆意图的旧原文摘录 | 4,500 字符 |
| 跨会话新增继承层合计 | 不超过 6,000 字符 |

预算耗尽时的保留优先级：

```text
用户确认事实 > 最新关键决策 > 约束与红线 > 未完成事项 > 最近脉络 > 历史建议
```

### 4.3 更新时机

- 每轮成功结束后异步增量更新；
- 每累计 20 条新消息或活跃事实超过阈值时做一次合并；
- 用户打开新会话时只读取检查点，不临时全量总结；
- 老会话无检查点时，使用最近 16 条和有限批次补建，补建失败不能阻塞回复；
- 摘要状态统一使用 §3.7 的 `DigestStatus + coveredThrough*`；不能再以一个 `caughtUp=false` 同时表达「尚未追平」「撞顶」「冷却」和「失败」。

## 5. 图片：从 4 张开放到 9 张

### 5.1 产品口径

- 用户单条消息最多选择 9 张图片；
- 图片和其他附件共用现有 9 份总附件上限；
- UI 显示“已选 X/9”；
- 超过限制时明确提示拆成下一条发送。

### 5.2 模型侧批处理

单次上游模型请求仍最多携带 4 张，9 张按 `4 + 4 + 1` 分批：

1. 每批输出带图片序号的结构化观察；
2. 保存批次观察，不把图片原始 base64重复塞进最终汇总；
3. 最后一轮只使用各批观察和用户问题生成综合回答；
4. 回答中可以引用“第 2 张”“第 7 张”，保证用户知道结论来自哪里。

成本与体验约束：

- 新增专用、短小的 `image_observation` 辅助提示词：每个图片批次只携带用户问题、图片序号和本批图片，不复用总军师完整 system prompt，也不携带完整会话历史。禁止实现时直接复用现有总军师调用链——那样每个批次都会重复携带完整大提示词，成本按批次数翻倍，“轻量上下文”就落不了地；
- 多批串行会拉长首字延迟，分批期间前端需给出进度反馈（如“正在阅读第 5～8 张”），不能让用户面对长时间空白。
- 图片观察、最终汇总都必须作为同一 GenerationJob 下可追踪的 attempt 持久化；进程重启后只补未完成批次，不重跑已经成功且已有观察结果的图片批次。

### 5.3 大小与失败保护

- 上传入口仍保留单张 10MB 硬限制；
- 推理前生成受控尺寸副本，最长边硬限制为 2048px；原件保留，存量图片首次使用时懒生成副本；
- 单个模型批次处理后的图片总大小不得超过 12MB；
- 一条消息全部图片处理后的总大小不得超过 24MB；
- 单张读取失败只跳过该张并告知序号，不能让整条消息静默失败；
- 每批独立超时、重试和记录 usage，但用户结算仍以整个 GenerationJob 聚合后的总 usage 一次完成；重试不得重复累计已成功 attempt 的结算量，最终汇总不得重复扣同一批次。

### 5.4 不属于复杂方案的条件

图片多不等于方案复杂。9 张门店陈列照片可能仍是一个单领域诊断；复杂度应由业务范围和交付物决定，而不是图片数量决定。

### 5.5 图片限制的运行时真源

`shared/contracts.d.ts` 是纯类型声明，运行时会被擦除，不能承载原生小程序和服务端共同读取的数值常量。图片限制采用“服务端权威 + 客户端保守兜底”：

- 下发通道使用现成的启动拉取接口 `GET /api/me`，新增 `capabilities.attachments`：`maxAttachmentsPerMessage`、`maxImagesPerMessage`、`maxImagesPerBatch`、单图/单批/单消息字节上限；`features` 只承载功能开关，不混入容量配置；
- 现状是两端各自硬编码、值一致纯属巧合：服务端 `MAX_REFS = 9`（`retrieval.ts`，超出会截断并生成 notices）、小程序 `REF_LIMIT = 9`，两者之间没有任何下发通道；
- `shared/contracts.d.ts` 只声明这些字段的类型，不保存运行时数值；
- 服务端始终按自身限制二次校验，客户端值只能改善交互，不能成为安全边界；
- 原生小程序在接口不可用时使用保守兜底值；
- 增加契约测试，锁住生产配置、mock 和原生兜底的兼容关系；
- 批次 D 前的过渡期，超过服务端可处理数量必须返回可见错误或明确 notices，禁止继续 `console.warn` 后静默截断。

## 6. 客户事实与用户确认机制

### 6.1 事实来源分级

| 来源 | 初始状态 | 是否可作为硬事实 |
|---|---|---|
| 用户本轮直接陈述 | `asserted` | 可以，保留原消息来源 |
| 用户点击确认或手动编辑 | `confirmed` | 可以，优先级最高 |
| 军师从资料抽取 | `pending` | 只能作为待核对线索 |
| 军师根据上下文推断 | `pending` | 不能写成客户事实 |
| 用户否认 | `rejected` | 禁止继续引用 |
| 被新事实替换 | `superseded` | 仅保留审计，不再注入 |

用户直接说“我们现在有 5 家店”本身就属于用户来源，不需要再追问一次。需要主动确认的是军师推断、资料抽取、冲突信息和高影响事实。

### 6.2 确认交互

系统在军师回复下方显示轻量确认卡，不要求用户专门输入“帮我记住”：

```text
我准备记住：目前有 5 家直营店，正在筹备第 6 家。
[确认无误] [改一下] [仅本次参考]
```

行为：

- `确认无误`：调用确认接口，状态改为 `confirmed`；
- `改一下`：展开一句话编辑，保存修正内容并将旧条目标记为 `superseded`；
- `仅本次参考`：不进入长期事实层，只保留在本次会话；
- 不操作：保持 `pending`，不升级为硬事实。

点击按钮不应发送一条假的聊天消息，避免污染会话和再次触发模型。自然语言“帮我记住”“不是 5 家，是 6 家”“这条别记”仍然需要支持。

### 6.3 什么时候弹

只在以下情况提示，每轮最多一张合并确认卡：

- 新旧事实冲突；
- 营收、门店数、预算、股权、团队规模等高影响事实；
- 军师推断或资料抽取准备进入长期档案；
- 关键决策即将写入交接包。

普通偏好、低风险信息和用户直接陈述不反复打断，避免把真人教练式对话变成表单。

### 6.4 数据要求

推荐新增独立 `UserFact`（或等价事实表），不要把确认状态直接塞进现有 `Memory`：`Memory` 仍承担语义召回、偏好和成果反馈，`UserFact` 承担可审计、可替代的客户硬事实。长期事实至少需要：

```ts
type FactStatus = 'asserted' | 'pending' | 'confirmed' | 'rejected' | 'superseded'

interface UserFact {
  id: string
  tenantId: string
  userId: string
  factKey: string
  valueText: string
  status: FactStatus
  sourceType: 'user_message' | 'document' | 'assistant_inference' | 'manual_edit'
  sourceMessageIds: string[]
  sourceSessionId?: string
  supersedesId?: string
  assertedAt?: string
  confirmedAt?: string
  supersededAt?: string
  createdAt: string
  updatedAt: string
}
```

`factKey` 是冲突识别与替代的前提，例如：

```text
company.store_count
company.annual_revenue
company.team_size
company.current_stage
strategy.current_positioning
```

“5 家店”与“6 家店”只有在 `factKey` 相同时才能建立明确替代关系；不能只靠文本向量相似度猜测冲突。模型可以从自然语言提取候选 `factKey + valueText + sourceMessageIds`，但状态转换、同 key 当前有效值、替代链和租户隔离由代码执行。

迁移口径：

- `StrategicProfile` 和用户手动编辑的档案字段继续作为既有权威事实；
- 旧 `Memory` 不做无依据的全量自动确认迁移，只在被用户重新陈述、手动编辑或明确确认后进入 `UserFact`；
- prompt 注入时，只有 `confirmed/asserted` 的当前有效事实可优先于语义 Memory；`pending` 仅展示在独立确认卡里，确认前绝不作为事实注入模型，`rejected/superseded` 同样不注入；
- 确认卡候选需要作为 `ChatReply` 的独立结构字段返回，并有专用确认接口；不能复用当前点击后会发送聊天文字的 `asks/chips` 协议。

实际落地时先修改 `shared/contracts.d.ts`，再修改 Prisma、服务端和小程序。

迁移注意：现有记忆近重去权逻辑会把命中条目的 `createdAt` 改写为当前时间，等于抹掉事实的原始发生时间，与本章“保留审计”的目标直接冲突。批次 C 落地时必须一并改掉（保留原始时间，另用独立字段记录最近强化时间），否则 `supersededAt` 等审计链会建立在被污染的时间戳上。

## 7. 报告触发优先级

### 7.1 统一输出意图

把当前分散的关键词判断收口成一个服务端真源，并把“用户想要什么”与“系统分几次交”拆成正交状态：

```ts
type RequestedOutput = 'report' | 'chat' | 'unspecified'
type DeliveryMode = 'single' | 'staged'

interface OutputDecision {
  requestedOutput: RequestedOutput
  deliveryMode: DeliveryMode
  deliveryStage: number
  complexityScore?: number
  complexityReasons?: string[]
}
```

优先级从高到低：

1. 用户明确要求报告、方案、计划、纪要或成果：`requestedOutput='report'`；
2. 用户明确说“先聊、先别出报告、不要方案”：`requestedOutput='chat'`；
3. 其他情况：`requestedOutput='unspecified'`；
4. 复杂度只决定 `deliveryMode='single'|'staged'`，不能覆盖明确输出意图。

例如“帮我做全国加盟扩张全案”应同时是 `requestedOutput='report'` 和 `deliveryMode='staged'`：第一轮立即出可独立使用的总纲报告，后续阶段由用户继续触发。不能用一个互斥枚举在“明确报告”和“分阶段”之间二选一。

否定意图必须先于正向关键词判断。这不是防御性设计，而是修复现状缺陷：当前正则没有任何否定分支，“先别出报告”“不用出方案”今天就会被 `出.{0,4}(报告|方案)` 命中而进入报告路径。此项可提前到批次 A 与批次 B 之间单独止血。

收口范围除 `sessions.ts` 与 `generationRequest.ts` 的两份字面量副本外，还包括 `mock.ts` 中的第三套不同正则，以及 `deliverableMode === 'on-demand'` 在 `sessions.ts`、`generationRequest.ts`、`generationWorker.ts` 中的多处内联判断。

### 7.2 明确要求报告时的行为

用户说“帮我出报告”后必须立即进入报告链路，不因为复杂度高而只返回追问。

如果资料不足：

- 先交一份可用的第一版；
- 明确哪些结论基于现有事实、哪些是暂定假设；
- 把最关键的 1～3 个缺口放在报告末尾；
- 提供继续深化的入口。

如果任务复杂：

- 第一轮仍交付完整可读的总纲版，而不是仅给目录；
- 后续按模块深化；
- 用户可随时停止，第一版仍能独立使用。

### 7.3 报告内容分阶段与生成分阶段

- `phases` 组件表示报告内容中的“第一阶段、第二阶段、第三阶段”；
- 分阶段交付表示多次生成不同模块或版本。

一份 4～10 章的报告完全可以包含三阶段打法。只有超出单份报告安全容量或包含多个独立交付物时，才拆成多次交付。

### 7.4 分阶段交付生命周期

分阶段不是模型在回复里随口承诺“下次继续”，而是持久任务链：

1. 第一阶段完成后返回本次已交内容、剩余阶段清单和“继续深化第 N 阶段”按钮；
2. 默认不自动启动下一阶段，只有用户点击或明确发话后才建单，避免未经授权连续耗时和扣额度；
3. 每个阶段创建独立、幂等的子 GenerationJob，复用 `parentGenerationId` 并冻结 `deliveryPlanId + stageKey + stageNumber`；
4. 同一个 `deliveryPlanId + stageKey` 的重复点击只能复用已有在途/已完成任务，不能重复生成和结算；
5. 每阶段独立预留并结算额度，按钮旁应说明会继续消耗本方案用量；
6. 用户可以停止，已交付的第一版仍必须可独立使用；
7. 重试、Worker 接管和客户端重进都沿用原 `requestedOutput/deliveryMode/stage`，不得重新分类后跳到别的阶段。

## 8. 复杂方案判定

### 8.1 不允许的判定方式

- 不能只看用户输入长度；
- 不能因为上传图片多就判复杂；
- 不能仅让模型返回“我觉得很复杂”；
- 不能把“资料不足”和“任务复杂”混为一项。

### 8.2 可解释评分

每个维度 0～2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 业务范围 | 单一领域 | 两个领域 | 三个及以上领域 |
| 独立交付物 | 一份 | 两份 | 三份及以上 |
| 时间与阶段 | 单阶段、30 天内 | 两阶段或 31～90 天 | 三阶段及以上或跨季度/年度 |
| 对象数量 | 单一产品/团队/地区 | 两个对象 | 三个及以上对象 |
| 依赖关系 | 已有资料足够 | 1～2 个关键依赖 | 多资料、多角色或 3 个以上关键依赖 |

路由：

- `0～3`：普通任务，单次交付；
- `4～6`：复杂方案，先总纲、再按模块深化；
- `7～10`：大型方案，建立明确交付清单和阶段状态；
- 明确要求 3 个以上独立成果时，直接判为复杂，不依赖总分。

执行边界：

1. 确定性规则先解析明确报告、明确聊天、明显的时间/交付物数量和否定意图；
2. 普通闲聊和单一明确任务不额外调用分类模型；只有规则命中“疑似复杂”的候选才进入模型逐维打分；
3. 维度打分由模型以结构化输出完成（逐维给分并给出理由，不允许直接返回“简单/复杂”结论），路由由代码按分数表确定；
4. 分类不得在 GenerationJob 建单前裸调用 provider。它必须是已建 GenerationJob 下可追踪的 `classification` attempt，记录 provider、usage、耗时和失败原因；
5. 分类有独立短超时，失败或超时默认 `deliveryMode='single'`，不能阻塞正常聊天；用户已明确要报告时先保持 `requestedOutput='report'`，分类失败也必须照常出第一版；
6. 分类结果和理由冻结进任务快照，Worker、重试和后续阶段只读取冻结值，不重复分类。

8.1 禁止的是“模型直接给结论并控制路由”，而不是“模型参与结构化打分”——纯规则无法完整理解自然语言里的领域数和交付物数，但代码必须掌握最终路由权和失败降级权。

每次判定需要记录得分与理由，例如：

```json
{
  "score": 6,
  "reasons": ["涉及品牌、增长、组织三个领域", "要求四个独立成果", "周期为一年"]
}
```

### 8.3 复杂度与资料齐备度分开

| 复杂度 | 资料状态 | 用户是否明确要报告 | 行为 |
|---|---|---|---|
| 简单 | 足够 | 任意 | 一次性交付 |
| 简单 | 不足 | 是 | 先交初版，标明缺口 |
| 简单 | 不足 | 否 | 追问 1～3 个关键问题 |
| 复杂 | 足够 | 是 | 立即交总纲版，用户确认后再深化 |
| 复杂 | 足够 | 否 | 说明交付路径并开始第一阶段 |
| 复杂 | 不足 | 是 | 立即交可用第一版，不阻塞在访谈 |
| 复杂 | 不足 | 否 | 先像真人教练一样澄清关键问题 |

### 8.4 示例

普通任务：

> 帮我出一份下个月单店抖音投流方案。

单领域、单对象、单份交付，直接一次出完。

复杂任务：

> 帮我做明年全国加盟扩张全案，包含品牌定位、获客、招商、组织、财务测算和 90 天启动计划。

涉及多个领域和独立成果，第一轮交扩张总纲版，后续深化招商体系、组织机制和财务模型。

## 9. 服务端路由设计（已实施）

一次请求的决策已收口为：

```text
确定性解析 requestedOutput
  ├── 明确报告 → 建单并立即走报告第一版
  ├── 明确对话 → 建单并走正常对话
  └── 未明确
        ├── 普通请求 → 正常对话
        └── 疑似复杂 → 建单 → classification attempt
                          ├── 结构化逐维评分
                          ├── 计算资料齐备度
                          └── 代码决定 single / staged
```

关键要求：

- `sessions.ts`、持久化生成建单和 mock 共用 `services/outputIntent.ts`，重复正则已删除；
- 生成任务冻结 `requestedOutput`、`deliveryMode`、复杂度得分和理由；需要模型分类时，先建 job，再把 classification attempt 的结果原子写回冻结快照；
- Worker 只读取建单期冻结的 `job.kind`，不再根据用户文字重新计算 `willDeliver`；
- 摘要覆盖状态、输出意图和阶段都属于本轮冻结上下文的一部分；
- 重试沿用原意图和原阶段，避免第一次出报告、重试却变聊天；
- 阶段状态必须持久化，不能只存在客户端；后续阶段采用 §7.4 的用户确认建单与幂等键。

## 10. 可观测性

可观测性按真源分层，不把不同生命周期的数据硬塞进一个 JSON：

```text
LlmTrace identity:
  createdAt / agentKey / versionId / provider / model / endpointId / endpointLabel
LlmContextTrace.continuity:
  sessionId / lineageId / continuationOf / sourceSessionId
  newChapter / chapterGapHours / inheritedChars
LlmContextTrace.digest:
  status / coveredThroughMessageId / coveredThroughAt
  pendingMessages / items / injectedChars
LlmContextTrace.history:
  recentMessages / carryoverMessages / totalChars
LlmContextTrace.routing:
  requestedOutput / deliveryMode / complexityScore / complexityReasons
  deliveryPlanId / stageKey / stageNumber
LlmContextTrace.images:
  imageCount / batchCount / completedBatches / skippedImageIndexes / totalBytes
GenerationAttempt:
  kind(classification 或 image_observation:n) / provider / usage / duration / outcome / resultJson
SessionDetail.page:
  pageSize / hasMore / nextCursor
```

后台诊断时必须能区分：

- 是总军师已发布 `AgentVersion`、实际 provider/model/endpoint 或部署版本发生了变化；
- 是没有继承交接包；
- 还是继承了但摘要未追平；
- 还是输入预算截掉了某类内容；
- 还是报告意图被错误分流；
- 还是复杂度分类失败或超时后按默认值降级；
- 还是多图某一批读取或生成失败；
- 还是长会话详情分页/端上渲染成为瓶颈。

## 12. 验收标准

### 12.1 连续会话

- 一条已有 220 条消息的总军师会话，闲置超过 24 小时后再次进入；
- 页面视觉上出现新篇章；
- 分隔只出现在跨 24 小时后的第一条用户消息前；隔天只打开未发送时显示底部临时分隔，军师延迟回复不会被误判成新篇章；
- 第一轮能说出至少一条客户事实、一条已定决策和上次未完成事项；
- 不要求用户从头介绍自己；
- trace 显示旧摘要已注入、`digestStatus='caught_up'`、`pendingMessagesBeforeCurrent=0` 且未撞顶，最近原文不超过 16 条、字符未超预算（Token 预算在 P1 切换 tokenizer 后再纳入验收口径）；
- 1,000 条消息会话首屏只取尾页，响应和渲染稳定；上拉可无重复、无遗漏地读回更早消息，分页接缝的章节分隔正确；
- 军师自己的历史错误推断不得作为客户事实复述。

自动化验收边界：当前已覆盖 205 条全部同毫秒消息的三页复合游标无重无漏、跨 24 小时章节冻结，以及 1,000 条摘要持续更新。上述“1,000 条消息会话响应与渲染稳定”仍是预发真机验收项，未完成前不能写成已验证的用户体验结论。

### 12.2 事实确认

- 用户直接说“目前 5 家店”后不反复弹确认；
- 军师推断“经营十年”时只能进入 `pending`；
- 用户把“5 家”改成“6 家”后，旧事实变为 `superseded`；
- 点击确认不产生一条假的聊天消息；
- “这条别记”“帮我记住”自然语言可正确更新状态。

### 12.3 报告与复杂方案

- “帮我出报告”立即返回报告；
- “先别出报告”只能返回对话；
- 简单任务一次交付完成；
- 复杂任务第一轮交付可独立使用的总纲版；
- 同一复杂请求可以同时记录 `requestedOutput='report'` 与 `deliveryMode='staged'`；
- 普通闲聊不产生 classification attempt；疑似复杂任务的分类有 usage/耗时/失败记录，超时后仍能正常回复；
- 后续阶段不自动运行，用户点击“继续深化”才创建唯一子任务，重复点击不重复生成或结算；
- 复杂度得分和理由可在 trace 查看；
- 重试不改变输出意图和阶段。

### 12.4 图片

- 用户可以选择 9 张图片；
- 任一上游请求不超过 4 张；
- 最终回答覆盖所有成功读取的图片并能引用序号；
- 一张失败时明确告诉用户是哪一张，其余图片仍可完成分析；
- 图片观察批次使用专用轻量提示词，不重复注入总军师完整 system prompt；
- 进程在第 2 批后重启时，只恢复未完成批次，前两批不重复调用；
- 总字节、批次延迟、每个 attempt 的 Token 和 GenerationJob 聚合结算均可观测。

### 12.5 摘要上限治理

- 造数使增量索引越过合并阈值，活跃态合并后仍能继续抽取新消息，不进入永久 capped；
- 合并前后保留最新事实、关键决策、约束和未完成事项，低优先级旧建议按规则淘汰；
- 每条活跃事实仍能追到真实来源消息；
- 合并中途崩溃后可幂等重试，游标不跳过消息；
- 两个 Worker 并发更新同一会话不会丢项、覆盖新版本或重复合并。

### 12.6 “像真人教练”的体验验收

- 测试对象必须是生产同款 provider、总军师当前已发布提示词与真实运行时上下文，不能用 mock 或仓库 seed prompt 代替；
- 至少 20 组脱敏样本应同时覆盖：同题方案咨询、隔天续聊、用户做对/做错的判断、资料不足追问、明确要报告、先别出报告和复杂方案；
- 新旧版本采用隐藏版本信息的成对盲测，人工逐项判断：是否记得关键事实、是否先接住处境、是否有明确取舍、语气是否有人情味、洞见是否基于事实且有惊喜、下一步是否具体；
- 自动评测使用 `COACH_QUALITY_RUBRIC` 作为回归信号，但不得代替人工偏好；真人教练感综合偏好率低于 60%、事实使用退步或编造率上升，任一项都阻断放量；
- 上线后按版本记录用户负反馈和重问率，出现同类“没之前聪明/AI 味变重”聚集时，先核对实际 provider、已发布 AgentVersion、运行时上下文 trace 和输出意图，不只看仓库提示词。

## 13. 产品默认决策

如无进一步拍板，实施默认值如下：

1. P0 采用“同一服务端 Session、前端视觉分章”；分界按真实消息时间即时推导，不创建假消息；
2. P0 同步把会话详情改为最近 80～100 条首屏加游标向上分页，不能继续一次返回和渲染全部历史；
3. 摘要状态改为 `caught_up/pending/capped/cooldown/failed/unknown` 和覆盖游标；滚动合并必须在任何活跃会话接近 350 条摘要项前上线；
4. P1 才创建真正独立的新 Session，并通过 `SessionHandoff` 继承确认事实、关键决策和最近脉络；
5. 图片一次最多 9 张，上游每批最多 4 张；运行时上限由服务端能力接口下发，`shared/contracts.d.ts` 只声明类型；
6. 事实层独立新增 `UserFact + factKey`；用户直接陈述默认记为 `asserted`，不重复确认；
7. 推断、资料抽取、冲突和高影响事实才弹确认；旧 Memory 不批量升级为已确认事实；
8. `requestedOutput` 与 `deliveryMode` 是两个正交维度；用户明确要求报告时立即进入报告链路，复杂度只决定一次交完还是分阶段；
9. 普通对话不调用复杂度分类模型；只有确定性预筛命中的候选请求才做结构化逐维评分，由代码按分数表路由，分类失败或超时默认单次交付；
10. 复杂度达到 4 分或要求 3 个以上独立交付物时默认分阶段；
11. 分阶段交付的第一版必须能独立使用，不能只交目录或让用户继续填表；
12. 后续阶段不得自动连续生成，只能由用户明确点击继续；每阶段独立建单、幂等、可恢复并单独核算用量。
