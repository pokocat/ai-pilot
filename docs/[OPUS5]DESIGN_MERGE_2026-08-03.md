## 合并原则

设计稿是视觉与信息架构基准，**不是数据基准**。凡设计稿里写死的用户侧数字（4 家主体、286 张人脉卡片、本月可用 2 次深度报告、¥299/¥199 月付）一律不落代码：

- 有后端字段的 → 接真实字段（三势、命盘、决策账本、算力用量、案卷缺口）；
- 没有后端字段的 → 落零态 / 待建立态 + 清楚的下一步，不摆示例数据；
- 定价与权益 → 走方案与权益页（运营后台是定价唯一真相源），页面上不印价格。

## 本轮刻意没做

1. **「为实体发声」与「矩阵管理」两个小程序**。设计稿第 15683 行是顶部小程序切换器（AI军师 / 为实体发声 / 矩阵管理），它们是**独立小程序**，不是本包内的路由。按业务方决定：本轮只在锦囊「账号与数据」保留「账号矩阵 · 待上线」入口，不实现本体。
2. **公司与事业架构的条件隐藏**。设计稿由 `state.architectureEnabled` 控制（战略报告识别到多主体需求后才亮入口）。后端没有这个识别信号，因此菜单行常驻显示并落「待建立」态——不做假的条件隐藏。
3. **持续记忆的真实数据面**。五个记忆来源（个人微信 / 企微 / 会议 / 日历 / 朋友圈）只有开通说明与读取范围，没有导入管道、待校对区、创始人动态档案和人脉卡片列表——这些需要新表 + 新端点。
4. **企业服务的办理进度**。六条服务线只有静态路径示意，没有用户侧进度（设计稿的「资料待补 / 类别建议中 / 待出方案」是 per-user 状态，无数据源）。
5. **设计稿的四级子 tab**（经营战局内再分 判断 / 三势 / 证据 / 行动）。小程序里在 mode tab 下再套一层 tab 太重，证据区改成页内「判断依据」区块。
6. **智库上传管道的 V2 改动**（`data-upload-*` 一族新属性、已优化文件的 AI 复核态）未逐条对齐——现有三段式管道（V7-06）功能上已覆盖，差异是交互细节。

### 二、出生地：后端一直通，前端从没收集过（回归）

证据链闭合：DB 有 `birthPlace`/`longitude` 两列 → `paipan.ts:169` 真太阳时校正（经度平太阳时 + 均时差 EoT）完整 → `cityLongitude` 已接在 `PUT /profile/bazi` → **命盘报告页已经在渲染「出生地」行和「真太阳时已校正」徽章** → 但三个生辰表单一个都不传。`git log -S birthPlace` 显示这个输入框在 M1 PR-2 时有（placeholder 写着「选填，用于真太阳时校正」），被后来两次改版丢了。所以那枚徽章**任何真实用户都点不亮**。

影响面不可忽略——时辰颗粒 120 分钟，而平太阳时偏移：乌鲁木齐 −129.6 分（超一整个时辰）、拉萨 −115.6、成都 −63.6、西安 −44.4。西部用户时柱系统性算错；落在子时/立春边界还会连日柱年柱一起错。

| # | 改动 | 说明 |
|---|---|---|
| 1 | `cityLongitude` 收紧匹配 + 改返 `matchCity()` | 旧的反向包含 `city.includes(s)` 会让「南」→南京、「海」→上海、「长」→**长沙**（不是长春）、「南京路」（上海路名）→南京。现口径：精确 → 输入含城市名取最长命中，单字一律不匹配。新增 `server/test/cityLongitude.test.ts` 钉住 |
| 2 | `paipan.ts` 分钟进位改 UTC 构造 | 原 `new Date(y,m,d,h,min+off)` 走服务器本地时间，**实测** `TZ=America/Los_Angeles` 下 2021-03-14 02:57 被静默平移成 03:57（整整一小时，足以改时柱）。生产在 Asia/Shanghai 碰不到，但与「同输入同输出可复算」矛盾。补了跨 TZ 断言单测 |
| 3 | `trueSolarApplied` 语义 | 原按 `offsetMin !== 0` 判定，杭州这类近 120° 的城市全年有约十天偏移抵消为 0，那几天徽章显示「未校正」是错的暗示。改为有经度即 true |
| 4 | `validatePaipanInput` 补校验 | `birthPlace` 长度上限 20（与前端 maxlength 对齐）、`longitude` 类型与范围。原先字符串 `"121.5"` 静默不校正、`NaN` 一路落库让 Prisma 抛错，被外层吞成「生辰无法排盘，请检查日期」——错误信息与真实原因无关 |
| 5 | 三个表单加出生地 | `mingpan` / `calendar` / `gift`，选填 |
| 6 | `/cards/fate/preview` 补查城市表 | 这条支路以前直接 `computeChart`，同一份生辰「自己的命盘」校正、「送朋友的卦」不校正，两处四柱可能不同 |
| 7 | `PUT /profile/bazi` 回 `matchedCity` | 前端据此 toast「已按成都校正真太阳时」或「未识别『老家』，按北京时间排盘」——不让「填了但没生效」悄悄发生 |
| 8 | 命盘报告头补未校正态 | 原来只在 true 时亮徽章、false 时一片沉默，等于默认让用户以为自己的盘已经最准。现在显示「按北京时间排盘 · 未做真太阳时校正 / 补出生城市可提升时柱准确度 ›」并可点回表单。缺时辰时不提（经度本就不参与计算） |
| 9 | mock 消费 `birthPlace` | 原先只把 body 整包存下、返回与入参无关的固定样例盘（`trueSolarApplied` 写死 true）——**这正是缺口藏这么久的原因：本地/H5 走查完全看不出来** |

**为什么是选填不是必填**：强制必填会逼出「本地」「老家」这类垃圾输入，而算错一次的代价是整盘重算（换日主/换年柱），比不校正严重得多；且缺时辰时经度根本不参与计算（`hourKnown` 是第一个与条件），必填会出现「填了但不参与计算」的荒诞态。取而代之的是强提示 + 识别回执 + 未校正态显式标注。

### 三、第 0 号军令点进对话丢了问题（2026-08-03 晚）

用户报：军令页「第 0 号军令」显示「你的公司、门店或品牌叫什么？」，点「去军师对话」进去，发出的却是「帮我补齐军师档案：你先问我最关键的 1-3 个问题，我来答。」

根因：卡片**显示**的是 `understanding.nextQuestions[0]` 这条具体问题，**动作**却硬编码了一句批量话术，两者没有关联。用户的观感是「我明明点了这条，它却装作不知道，还要再问我一遍」。同一处错误有三个位置：

| 位置 | 原来 | 现在 |
|---|---|---|
| 军令页 第 0 号军令卡 + 今日焦点 | 显示 `nextQuestions[0]`，发批量话术 | 发 `archiveAnswerPrompt(nextQuestions[0])` |
| 军情页 待补证据（3 行，每行一条问题） | **每行都调同一个 `startInterview`**——行是分开的、动作却是同一个，点第 3 条也只收到批量提问 | 每行发自己那条 |
| 老板页 档案工作台「当前最该补」 | 一律跳智库上传 | 按 key 分流（见下） |

口径收进 `data/intents.ts`，两条不许再混：
- `ARCHIVE_INTERVIEW_PROMPT` —— 聚合入口专用（军情「待补资料 N」指标格、军令「待补资料」计数格），不指定哪条。
- `archiveAnswerPrompt(q)` —— 具体问题专用，把原问题原样带进去。空问题自动退回批量，不发空指令。

**顺带修掉一个契约漂移**：`workbench.missing` 混了两类东西——服务端 `community.ts` 用 `next-N` 标记「要在对话里回答的问题」，用 `pricing/funnel/proof` 标记「要上传的资料」。老板页据此分流，但 **mock 用的是 `q0/q1/q2`**，于是同一段代码在本地走查跳智库、在线上跳对话。已把 mock 对齐到 `next-${i+1}`。

回归：`app/src/data/intents.test.ts` 4 条（原问题必须出现在 prompt 里、不同问题产出不同 prompt、空问题退回批量、两条话术彼此不同）。

**发现但未修**：对话页每次渲染都会抛一个 `TypeError: Cannot read properties of undefined (reading 'map')`（`msgs.map` 回调内部）。把全部工作区改动 stash 后重建，错误依旧——是既有问题，与本轮无关，已单独立项。

### 四、生辰录完不能改（2026-08-03 晚）

用户报：八字录完就定死了。核实属实——**命盘完整时，全 App 没有任何入口能改生辰**。

生辰是整盘的唯一输入（四柱、旺衰、格局、紫微、大运、年度攻守、三势天势全从它派生），录错一个数字就是永久错。原来能打开表单的只有三条路，全都是「残缺态」专属：

| 入口 | 触发条件 |
|---|---|
| `needBazi` | 完全没有命盘 |
| 「补录时辰 · 立紫微盘」 | `ziwei === null`，即缺时辰 |
| 「未做真太阳时校正」提示（本轮新加） | `!trueSolarApplied && hourKnown` |

有时辰 + 已校正 = 三条都不满足 = 改不了。天时日历页更彻底：表单只在 `!chart` 时渲染，有盘之后连残缺态入口都没有。建档流的 `Picker` 也只在 `first` 时走到 bazi 步骤。

后端本来就支持覆盖（`PUT /profile/bazi` 覆写 `extraJson.bazi` + `computeAndStoreChart` upsert 单行命盘），纯前端缺口。

改动：

| # | 改动 | 说明 |
|---|---|---|
| 1 | 命盘报告档头常驻「生辰录错了？修改并重新立盘 ›」 | 弱化样式，不与报告正文抢注意力，但**始终在** |
| 2 | 表单从已存生辰**预填** | 原来「补录时辰」打开的是空表单，等于让用户为了补一个时辰把年月日性别全部重敲 |
| 3 | 预填读 `api.myChart()` 的 **bazi 原始输入**，不读 `report.base` | `base.solarDate` 是真太阳时校正**之后**的排盘日期，拿它回填等于把校正结果当输入再校正一次，**改一次漂一次** |
| 4 | 改生辰时按钮改「更新生辰 · 重新立盘」并给「取消」 | 首次录入不给取消（没盘可回）；改的时候必须能退出去 |
| 5 | 天时日历加一行指向命盘报告 | 生辰只保留一个编辑处（同一去处只留一个入口），本页不重复放表单 |
| 6 | `mock.myChart()` 的 `bazi` 从 `object` 改回 `BaziBody` | 联合类型被 mock 分支拖宽成 `object`，调用方按字段回填直接编译不过 |

实测（H5 mock，造一份「有时辰 + 已校正」的完整盘——原来毫无入口的状态）：入口出现 → 点开预填出 1990/6/18/四川成都/阳历/巳时/男 → 改日 18→19、时辰 巳→午 → 提交后落库为 `{year:1990,month:6,day:19,hour:12,birthPlace:'四川成都'}`，表单自动收起、入口回位。天时日历那行点击正确跳到命盘报告。

**未做**：改生辰后不重算年度谶语。谶语按「一年一句」守卫生成（`routes/profile.ts:141`），并带 `verseMoments` 点谶历史与 `verseHistory` 归档——改盘后旧谶确实是按错盘出的，但静默换谶会连带毁掉点谶记录，属于留存机制的产品决策，没有擅自改。
