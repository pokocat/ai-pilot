## 1. 三层声音（本方案的核心规则）

| 层 | 谁在说 | 覆盖范围 | 人称 | 语气 | 示例 |
|---|---|---|---|---|---|
| **L1 系统层** | 产品系统 | Toast、错误提示、支付、额度、到期、免责声明、上传/处理状态 | 无人称 | 中性、准确、可操作，**零角色扮演** | 「军情已更新」「本月额度已用尽」 |
| **L2 界面层** | 用户在发起动作，或界面在标记位置 | 按钮、标题、菜单、标签、纯状态空态 | 按钮可用「帮我」；其他通常无人称 | 短、清楚、先说动作或结果 | 「帮我出今日军令」「还没有案卷」 |
| **L3 军师层** | 军师本人 | 对话、问候语、memText/learnText、判词、军师叙述型空态/加载态、报告开场、复盘说明 | **第一人称「我」** | 有阅历、有判断、替你着想，但不过度演戏 | 「你的情况我记着，判断才有根有据」 |

**人格只活在 L3。** 用户在报错、扣费、额度用尽时要的是知道怎么办，不是听军师俏皮话；反过来对话里还用「系统已为您生成」就白建了人设。

### 硬规则一：按钮由用户发话；提示先判断是系统状态还是军师叙述

按钮是用户在对军师说话：

- ✅ 「帮我出今日军令」「帮我写脚本」「就按这个来」
- ❌ 「我给你排今日安排」（军师在按钮里自述，点起来别扭）

纯结果提示走 L1，不加人设：

- ✅ 「资料已入库」「发送失败」「本月额度已用尽」
- ❌ 「我替你收好了」「这回合没接住」（结果不够准确，也不知道下一步怎么办）

只有明确放在军师上下文中的空态 / 加载态才走 L3，用第一人称，并**去掉第三人称自述**：

- ✅ 「还没给你立过案卷」「容我想想…」
- ❌ 「军师还没为你建档」「军师正在思考…」（「军师正在 XX」是全站最重的 AI 味）

### 硬规则二：古意留在名词，白话留在动词；禁短语，不做单字封杀

- **保留**（用户已学会的产品名词，不要动）：军令、案卷、三势、锦囊、复盘、参谋室、军师、战局
- **改写**（当它们作为系统动作或空泛动词时）：数据沉淀、能力调用、动态校准、模型产出、付费解锁、持续赋能、自动对齐、可执行的、结构化
- **保留**（已经建立认知的产品名词）：产出额度、方案与产出额度、已启用、专项能力；后台、接口、代码字段不因用户文案改写而强行改名
- **不新增**古装动词：呈送、呈上、候着、一盏茶功夫、这回合、营生

名词撑世界观，动词一旦文言化就变成 cosplay。

### 硬规则三：一词一译

同一概念全站只有一种说法。来源文档里「认可」出现了 `就按这个来`/`拍板定案`/`这方案靠谱`/`照此行事`/`方案定了` 五种，一律收敛。

### 3.0 先认运行时真相源，再改文案

下面的文案表是**目标口径**，不是“只改表中这个文件”的指令。不同文案抵达用户的路径不同，落地时必须按下表同时处理：

| 文案类型 | 运行时真相源 | 仓库种子 / 离线镜像 | 生产落地要求 |
|---|---|---|---|
| 智能体 `greet`（§3.1） | 数据库 `Agent.greet` 草稿 + `publishedVersionId` 指向的 `AgentVersion.greet` 快照 | `server/src/data/agents.ts`＝新建 agent 初值 **＋ 离线镜像来源**；`app/src/data/agents.ts` 在 mock / 离线模式下是用户真看得见的 greet | 先确认该 agent 没有待发布的无关草稿；再走运营后台逐个编辑草稿 → 沙盒验收 → 核字段 diff → 发布新版本。改 seed 不会改变既有环境，但**必须同步改**，否则 mock / 离线包仍是旧文案。详见下方「greet 红线」 |

> 生产环境的智能体行为与展示文案受已发布版本保护。修改仓库种子不会自动改变线上已发布版本；反过来，后台更新草稿但不发布也不会改变 C 端。实施记录必须写明“改了哪一层、发布了哪个版本、在哪个环境看到了什么”。

#### greet 红线：禁用 `--force-prompts`

`greet` 与 `systemPrompt` 在 `server/scripts/syncAdminContent.ts` 里同属 `OPERATOR_OWNED`（“运营在后台调教过的字段：create 写初值，update 默认不碰”）：

- update 分支**默认跳过** `greet`。改完 `server/src/data/agents.ts` 再跑 `admin:sync-content`，14 条 greet 一条都不会进库。
- 唯一的覆盖开关是 `--force-prompts`，它还带 `SHRINK_REFUSE_RATIO = 0.8` 护栏：仓库值比库里短 20% 以上才 refuse。这个护栏只挡粗粒度误配，不能代替“不使用 force”的流程纪律。
- **最危险的是它对 `systemPrompt` 和 `greet` 同时生效。** 2026-07-28 已纠正早先的单位错误：`general` 生产为 49,094 **字节** / 19,486 UTF-8 字符，仓库为 44,959 字节 / 17,232 字符，实际差异是 +9.2%（字节）/ +13.1%（字符），不是 2.85 倍；其余 9 个专业 agent 当时逐字节一致。由于 13.1% 小于 20%，对 `general` 使用 force 时护栏**未必会拒绝**。
- 历史 `AgentVersion` 是不可变快照，旧版本不会被 force 覆盖，且支持 `rollbackToVersion`。准确风险是：force 先把当前 `Agent.systemPrompt` 草稿覆盖成仓库旧稿，后续一次不谨慎的发布会把旧稿生成错误的新版本并切给 C 端。虽然可以回滚已发布指针，草稿中的线上增量仍需从变更前备份恢复。

> ✅ **`server/scripts/syncAdminContent.ts` 的头部注释已于 2026-08-01 修正**（P0-0 项，`docs/CHANGELOG.md` 有记录）。保留这段记录，是因为错误本身值得复盘：
>
> 原注释写着「线上 49,094 **字符** / 仓库 17,230 / 已漂 2.85 倍」「其余 agent 线上 1,650–1,764，本地 620–670」。那是字节与字符混算的结果——1,650÷620≈2.66 恰好是中文 UTF-8 的字节/字符比，说明当时对比的两侧单位不同，内容其实一致。
>
> 这个错误注释比数字本身更危险：它让人误以为「差 2.85 倍 → 护栏必然 refuse」，从而放心使用 force；而按真实字符数 `17,232 / 19,486 = 0.884 > 0.8`，`decidePromptWrite` 会走 **write，不是 refuse**。现注释已改为正确单位与数值，并把「默认跳过 `OPERATOR_OWNED`」的理由换成「线上是运营调教资产，且实际差异不触发护栏」。同一个错误结论已被引用两次，第三次到此为止。

**结论：本次文案变更全程禁止 `--force-prompts`。** greet 走后台逐个编辑草稿，seed 里同步改一份仅供新建 agent 取初值和前端离线镜像对齐。

开工第一件事是把每个 agent 的**草稿 greet 与当前已发布 greet 分开导出**，同时记录 `publishedVersionId/version` 与 `draftDirty`。不要用 `--dump-prompts` 完成这件事：现有命令读取的是 `Agent` 草稿，不是 C 端已发布快照，而且会连同所有完整 `systemPrompt` 一起写盘。

备份必须满足：

1. 输出目录由 `mktemp -d` 建在仓库外，不写 `docs/_backup`，不纳入 Git；
2. 只导出本次需要的公开文案字段，不导出完整 system prompt；另行记录 `systemPrompt` 的 SHA-256，供发布后确认内容未变；
3. 草稿 greet 取后台详情，已发布 greet 取有效 `AgentVersion` 或发布态 `/agents` 回读；
4. 若 `draftDirty=true` 或草稿与已发布版本除本次字段外还有差异，先处理/归档原草稿，本次不得直接发布。

改动前再用 dry-run 确认这次同步不会碰到运营资产：

```bash
cd server && npm run admin:sync-content -- --dry-run
```

#### 发布红线：先清理已有脏草稿，再做单字段发布

后台发布不是“只发布刚改的那句话”，而是把当前整份 `Agent` 草稿冻结成新的 `AgentVersion`。因此每位 agent 开始改文案前都要做一次发布前置检查：

1. 记录当前 `publishedVersionId/version`、`draftDirty`，并导出草稿与已发布版本的本次目标字段；
2. 比较草稿和已发布版本的完整可发布字段。若已经有与本次无关的 prompt、模型、运行参数、权益或交付物改动，先由原负责人决定发布、撤回或另行留档，本次不得夹带；
3. 文案改完后再次核 diff，允许变化的字段仅限本批次台账列出的 `greet/memText/learnText`；
4. 沙盒通过后再发布，并回读 `/agents`、会话详情和版本号确认 C 端确实使用了新快照。

这条检查适用于后台手工改 `greet`，也适用于补齐窄字段编辑能力后的 `memText/learnText`。任何一步发现无关差异，都暂停该 agent 的发布，不用 `--force-prompts` 或全量 sync 去“顺手拉齐”。

> 生产前置快照确认：当前 14 位 agent 的 `draftDirty` 均为 false；`general` 与 `poster` 有已发布版本，其余 12 位尚无 published version。对首次发布的 agent，没有历史快照可做“版本间 diff”，必须把开工前的干净 `Agent` 草稿快照视为基线，发布前比较整份可发布字段，仅允许本批文案字段变化。

#### 镜像红线：完整对象生成器缺失，文案字段已由专用同步器收口

原先 `AGENTS.md` 声明 `app/src/data/agents.ts` 与 `app/src/data/deliverables.ts`「由后端 seed 自动生成，勿手改」，但仓库里没有对应生成器。现已新增 `server/scripts/syncAppCopy.ts` 与 `npm run copy:sync`，只负责本批文案字段；完整对象生成器仍不存在。

不要去找一个不存在的命令，也不要直接做“完整公开字段深比较”。当前镜像已经存在与文案无关的历史差异，至少两条轴：

- **`enabled`**：服务端 seed 里 `intel / fund / model / org` 四个都是 `enabled:false`（D-8 军师收编 4+1），前端镜像里 14 个全是 `enabled:true`；
- **`owned`**：镜像把 `general / strat / growth / fund / ip` 硬编码为 `owned:true`，其余 false——服务端 seed 根本没有这个字段，它是纯前端离线兜底的产品取值。

直接要求全字段一致，会迫使文案 PR 顺带改变 mock 目录、货架和权益行为。

本次已按以下最小路径落地：

1. `server/scripts/syncAppCopy.ts` 按 agent key 只同步 `greet/memText/learnText`，并同步 `REPLIES['默认']`；明确禁止改 `enabled/gift/billing/price/owned/deliverableKey` 等行为字段。
2. `npm run copy:sync -- --check` 只比较上述文案字段，不比较当前存在产品差异的完整对象；不一致返回非零退出码。
3. 本次所有镜像变更均由同步器产生，禁止手工双写。完整镜像生成器与现有行为字段漂移另立任务，先做产品决策再统一。

> **`--check` 的保护范围要写进脚本自身的 usage 与 `AGENTS.md`**：它只覆盖本批次的 `greet / memText / learnText` 与 `REPLIES['默认']`。`DELIVERABLES` 全表、agent 的 `enabled/owned/billing/price` 等行为字段**仍然无守卫**，尽管两个镜像文件头部都写着「自动生成，勿手改」。不写清楚，下一个人会以为动镜像有 CI 拦着。

### 3.1 智能体问候语 greet（后台编辑草稿 → 发布）

保留 14 位军师的花名与专业分工，但把初版中过强的江湖腔收半档：有判断、有动作，不命令用户，不暗示包装事实，也不对竞争对手作无依据的贬损。

> **落地方式：运营后台逐个编辑草稿，不走 seed。** `greet` 是 `OPERATOR_OWNED` 字段，`admin:sync-content` 默认跳过；`--force-prompts` 本次禁用（见 §3.0「greet 红线」）。表中行号仅用于定位仓库里的旧文案，不代表改这个文件就生效。

>

### 3.2 智能体 memText（扩窄字段编辑能力 → 草稿 → 发布）

> **不要用全量 `admin:sync-content` 更新既有环境。** 2026-08-01 的定价治理已把计价字段（`gift/billing/price/billingRatio/meterUnit`）拆进 `pricing`，update 默认不写、需 `--force-pricing`——所以「跑一次全量同步会打回线上定价」这条**已经不成立**。但 update 分支的 `structural` 仍会无条件写入：

>

## 8. 结论溯源：本稿改过的错判，及其复核方法

这份方案在评审中推翻过四个看起来很合理的结论。它们不是笔误，而是**同一类推理捷径**：拿一份二手描述当事实，只读到相关字段就下判断。下面逐条记下错判、真相、以及一条可复用的复核动作——再有人（或任何 AI 助手）接手这份文档时，先过这张表。

| # | 曾经的错判 | 实际情况 | 下次的复核动作 |
|---|---|---|---|
| 1 | 「线上 systemPrompt 比仓库漂了 2.85 倍」——直接引用了 `syncAdminContent.ts` 的头部注释 | 字节与字符混算。真实差异 +13.1%（字符）。旁证：注释自己写的「线上 1,650–1,764 / 本地 620–670」比值 ≈2.66，正是中文 UTF-8 的字节/字符比 | **代码注释是二手描述，不是事实来源。** 引用任何注释里的数值前，自己量一遍，并明确单位（字节 / UTF-8 字符 / UTF-16 code unit）。比值接近 2.6–3.0 时先怀疑单位不一致 |
| 2 | 「新 greet 更短，`--force-prompts` 会被 `SHRINK_REFUSE_RATIO` 护栏拒掉」 | `17,232 / 19,486 = 0.884 > 0.8` → `decidePromptWrite` 返回 **write**。护栏不会拦 | **不要从错误的量级推导安全结论。** 涉及护栏、阈值、限流时，把真实数字代进判定函数算一遍，而不是凭「差得多」「差不多」定性 |
| 3 | 「改 seed + 跑 `admin:sync-content` 就能更新 `memText/learnText`」 | 技术上成立，但同一个 `structural` 对象还包含 `billing / price / billingRatio / meterUnit / deliverableKey / memoryConfig / sort / gift / name / role / icon / type / chipsJson`。为两句文案跑全量同步，会把仓库的定价与权益配置一起写进草稿，下一次发布即冻结 | **判断一条写路径是否安全，要读完它写入的完整字段集，不是只确认目标字段在里面。** 见到 `...structural`、`...spread`、`Object.assign` 就展开看全量 |
| 4 | 「补一个种子与镜像的完整公开字段深比较测试」 | 镜像已存在与文案无关的历史漂移（`enabled` 四个下架 agent、`owned` 五个硬编码），该测试会迫使文案 PR 顺带改变货架与权益行为 | **给存量代码加一致性断言前，先测一遍现状。** 现状不一致时，正确做法是缩小断言范围到本次字段，而不是要求现状去迎合断言 |

补充两条本稿反复用到的口径，也一并固定下来：

- **「仓库里写着 X」≠「线上是 X」。** 智能体的 `systemPrompt / greet` 以数据库为唯一运行时事实来源（见 `server/src/data/agents.ts` 头部 2026-07-28 定调），仓库只是新环境种子。任何关于线上文案的结论，必须有运行时证据（`/agents` 回读、版本号、后台截图），不能以源码代替。
- **「文件头写着自动生成」≠「真有完整生成器」。** 本次已补 `copy:sync`，但它只覆盖三项 agent 文案与默认回复；`enabled/owned/billing/price` 和 `DELIVERABLES` 全表仍不受保护。判断保障范围时必须读脚本实际处理的字段，不能从文件头推断完整镜像一致性。
