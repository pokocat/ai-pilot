# 军师 · 前后端错位发布策略（RELEASE_STRATEGY）

> 解决的问题：小程序从上传到审核通过需要数天，后端发布却是分钟级。两者节奏不可能对齐，
> 若按「先发后端再发小程序」朴素操作，中间必然出现新旧不兼容窗口。
> 本文给出兼容口径、发布顺序、契约演进方式与逐类改动的流程清单。
>
> 部署命令与主机细节见 `DEPLOYMENT.md`；本文只管**发什么、按什么顺序发、怎么保证不炸**。

## 0. 先对齐拓扑事实（常见误解）

| 说法 | 实际 |
|---|---|
| 「预发和生产不是同一台服务器」 | **军师自身是同一台**：`8.136.36.175`，生产 `:4000`（库 `junshi`）、预发 `:4001`（库 `junshi_preprod`），进程分别是 `junshi-api` / `junshi-api-preprod` |
| | **下游 AIStar Clip 才是两台**：生产 → `47.98.162.120` 公网 HTTPS；预发 → 同机 `127.0.0.1:8081` |

所以「两套环境隔离」的程度比直觉低：**同宿主机意味着资源争抢与宿主故障会同时打到两边**（2026-08-15 已发生过一次，见 `DEPLOYMENT.md` §8.1）。

但这不是本文要解决的难点。**真正的难点与服务器有几台无关。**

## 1. 真正的约束：新旧客户端长期并存是常态，不是窗口

小程序不像 Web 那样「刷新即最新」：

- 审核数天 → 这几天里线上跑的全是旧版本；
- 审核通过后也不是瞬时全量 → 微信按启动异步更新，用户可能继续用缓存的旧包；
- 灰度发布 / 分阶段发布时，新旧版本**按设计**同时在线；
- 用户可以长期停在旧版本（不主动重启小程序）。

**结论：不存在「切换窗口」，只有「长期并存」。** 于是唯一可持续的口径是：

> **后端在任意时刻，都必须能同时正确服务当前在架的所有客户端版本。**

一旦接受这条，"先发哪个"就不再是难题——因为后端本来就不许破坏旧客户端。

## 2. 三条铁律

### 铁律一：兼容方向是单向的

- **后端向后兼容旧客户端**：旧包发来的请求必须继续能工作。
- **客户端向前容忍未知内容**：对多出来的字段、没见过的枚举值要能忽略而不是崩。

新增字段用可选、给默认值；新增枚举时旧客户端要有兜底分支。

### 铁律二：发布顺序永远是「后端先行」

后端先发（且向后兼容），客户端后发。理由：

- 后端先行时的中间态是「新后端 + 旧客户端」——只要遵守铁律一，这是**安全**的；
- 客户端先行时的中间态是「旧后端 + 新客户端」——新客户端会调用不存在的接口、依赖没上线的行为，**必然出错**，而且这批客户端已经在用户手里，收不回来。

> 今天（2026-08-16）「锦囊确认即启用」就踩到过这个中间态：小程序预览包先推到了手机，
> 而生产服务端还是旧的收费逻辑。新客户端已删掉「余额不足」提示分支，旧后端仍会扣费 →
> 用户被静默扣钻石且只看到泛化报错。**这正是铁律二存在的原因。**

### 铁律三：用服务端开关把「发布」与「生效」解耦（对抗审核期的核心武器）

审核要数天，但**开关是即时的**。所以：

1. 客户端带着新功能代码过审，但功能由服务端开关控制，**默认关**（dark launch）；
2. 审核通过、版本铺开到足够比例后，运营后台**打开开关**，功能才对用户可见；
3. 出问题**关开关即可**，不需要再走一次数天的审核。

本仓库已有成熟的 `FeatureFlag` 设施（`server/src/services/featureFlag.ts`）：60s 内存缓存、
合规类开关直读 DB 保证多实例即时一致、支持 `payload` 承载分级参数、运营后台可改。
**缺的只是把选定开关下发给客户端**（见 §4）。

## 3. 契约演进：Expand → Migrate → Contract（扩展-迁移-收缩）

任何破坏性变更都拆成三步，**三步之间隔着「旧客户端流量归零」这道闸**：

| 阶段 | 后端做什么 | 客户端做什么 | 可否同期发布 |
|---|---|---|---|
| **Expand 扩展** | 新增字段/接口，与旧的**并存**；旧路径行为不变 | 不动 | 后端单独发 |
| **Migrate 迁移** | 双写/双读，新旧语义都支持 | 新版本改用新字段/接口；仍能容忍旧响应 | 客户端过审后发 |
| **Contract 收缩** | 删除旧字段/接口 | 不动 | **必须等旧版本流量归零**，通常数周 |

反面清单——以下都属于破坏性变更，**不许直接改**，必须走三段式：

- 删除或重命名响应字段、修改字段类型；
- 收紧请求校验（原来可选的参数变必填）；
- 改变枚举取值含义；
- 删除接口或改变其 HTTP 语义；
- 改变错误码含义（旧客户端按旧码做了分支）。

> **本次锦囊改动为什么是安全的**：服务端只是「不再扣费」，响应结构没变（`pricePaid` 保留、恒 0）。
> 旧客户端仍显示价格卡、仍按 `pricePaid` 展示，只是实际不扣——属于「少扣钱」，不产生资损。
> 这是典型的**行为收敛型**变更，可以后端先行、客户端慢慢跟。
> 若当时把 `pricePaid` 字段直接删掉，旧客户端就会拿到 `undefined` —— 那就是破坏性变更了。

## 4. 本仓库现状盘点与缺口

| 能力 | 现状 | 结论 |
|---|---|---|
| 客户端知道自己的版本 | ✅ 构建期注入 `app/weapp-native/config/env.js` 的 `VERSION` / `GIT_SHA` | 已有 |
| 客户端把版本告诉服务端 | ❌ `services/request.js` 只带 `content-type` 与 `x-user-id` | **缺口 P0** |
| 服务端功能开关 | ✅ `FeatureFlag`，缓存/合规直读/payload/后台可改，6 个模块在用 | 已有 |
| 开关下发给客户端 | ❌ 客户端启动不拉任何服务端配置 | **缺口 P0** |
| 最低版本 / 强更提示 | ❌ 无 | 缺口 P1 |
| 旧版本流量度量（何时可以 Contract） | ❌ 无版本上报就无从度量 | 随 P0 一并解决 |
| 客户端版本可回溯到 commit | ⚠️ `WEAPP_RELEASES.md` 有 SHA，但 git tag 只打了 4 个（0.2.34/35/36 缺） | 缺口 P1 |

### 建议补齐顺序

**P0-1 客户端版本上报**（改动极小，收益最大）
在 `services/request.js` 统一请求头里加 `x-client-version: env.VERSION`、`x-client-sha: env.GIT_SHA`。
服务端记录到访问日志/指标，即可回答两个关键问题：*旧版本还剩多少流量？现在能不能收缩？*

**P0-2 客户端可见开关下发**
在 `/me`（客户端启动必调）响应里加一个 `flags: Record<string, boolean>` 白名单字段，
只下发**明确标记为客户端可见**的开关，避免把内部开关泄露出去。客户端读不到时一律按「关」处理
（fail-safe：新功能默认不生效，而不是默认生效）。

**P1-1 每次上传打 git tag**
`weapp-v<version>`，与 `WEAPP_RELEASES.md` 的记录一一对应。
这样「用上一版客户端回归新后端」才有可寻址的起点（见 §5 的兼容性回归）。

**P1-2 最低版本提示**
服务端按 `x-client-version` 判断，过旧则返回可读提示，引导用户重启小程序更新。

## 5. 标准发布流程（按改动类型分三类）

> 本节管「谁先发、怎么保兼容」。每次动手时**逐条核什么**（配置活在库里、模型路由默认值、
> 构建从哪取源、验收打哪条链路）见 [RELEASE_SOP.md](RELEASE_SOP.md) —— 那份是 2026-08-17
> 一次「预发全绿、切生产就露」的连环故障复盘出来的核查清单，两份都过一遍才算完。

### A 类：纯后端改动（不需要客户端配合）

1. 预发部署 → 回归 → 生产部署（`DEPLOYMENT.md` §10）。
2. **必做的兼容性回归**：用**当前线上客户端版本**（不是最新代码）指向新预发后端跑一遍。
   做法：`git worktree` 检出上一版 tag → `npm run build:weapp:preprod` → auto-preview 到真机。
   这一步专门验证铁律一，是最容易被跳过、也最容易出事的一步。
3. 生产发布后核对 `.deploy-history`（见 `DEPLOYMENT.md` §10）。

### B 类：纯客户端改动（不依赖后端新能力）

1. 预发 API 构建 → 真机验收 → 上传开发版（`npm run release:weapp`）→ 补 `WEAPP_RELEASES.md` → 打 tag。
2. 提交审核 → 通过后发布。
3. 后端不动，无错位风险。

### C 类：前后端联动改动（本文的主场景）

```
第 1 步  后端改动写成「向后兼容 + 开关默认关」
         ├─ 新增字段/接口，不动旧路径
         └─ 新行为包在 FeatureFlag 里，默认 false

第 2 步  后端发预发 → 用【上一版客户端】回归（验证旧包不受影响）→ 发生产
         此时线上：新后端 + 全部旧客户端，功能未生效，用户无感

第 3 步  客户端改动上传开发版 → 真机验收（临时打开预发开关验证新路径）
         → 提交审核 → 等数天 → 审核通过 → 发布

第 4 步  等版本铺开（看 x-client-version 指标），确认新版本占比达标

第 5 步  运营后台打开开关 → 新功能对用户生效
         出问题：关开关即可回退，不需要重新过审

第 6 步  旧版本流量归零后（通常数周），才做 Contract：删旧字段/旧接口/旧分支
```

**关键点：第 2 步和第 5 步之间可以隔任意长时间，审核耗时被完全吸收。**

## 6. 灰度与回滚

| 手段 | 生效速度 | 适用 |
|---|---|---|
| 关 FeatureFlag | 秒级（合规开关直读 DB，普通开关 ≤60s） | **首选**，新功能出问题 |
| 后端回滚版本 | 分钟级 | 后端自身缺陷；预发有自动回滚，生产需手工 |
| 小程序回退版本 | 微信后台可回退到历史版本，但仍受客户端更新节奏影响 | 客户端严重缺陷 |
| 重新提交审核 | **数天** | 尽量避免——这正是要用开关的原因 |

**推论：任何有风险的联动改动，都应该让「关开关」成为第一道回滚手段，而不是让回滚依赖发版。**

## 7. 一页速查

- 后端永远先发，且永远向后兼容 → 中间态才是安全的。
- 破坏性变更一律拆成 Expand → Migrate → Contract，收缩前必须确认旧版本流量归零。
- 审核期用「客户端带 dark code 过审 + 服务端开关控生效」来吸收。
- 没有客户端版本上报，就无法知道何时可以收缩——这是当前最该补的缺口。
- 纯后端发布也要用**上一版客户端**回归一次，这一步最容易漏。
