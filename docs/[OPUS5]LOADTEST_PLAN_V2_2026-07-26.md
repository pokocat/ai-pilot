## 0. 为什么要重做：上一轮的四个结构性盲区

不是执行质量问题——隔离、护栏、清理都做得很干净。是**测试口径**让部分结论不可用。

### 盲区 1 · `NODE_ENV=test` 让限流层根本没跑

`loadtest/docker-compose.yml:32` 设 `NODE_ENV: test` → `isAiTestMode()` 为真 → `server/src/app.ts:73` 的
`if (!isAiTestMode())` **跳过了 `@fastify/rate-limit` 的注册**。生产会注册它，且因为缺 `trustProxy`，全站共用
一个 300/min 的桶（详见优化计划 P0-0）。450 RPS 这一档从头到尾没经过限流层，这个缺陷压测在结构上不可能发现。

### 盲区 2 · API 容器被 `cpus: 2.25` 限死，"单进程到顶"这个结论不成立

`loadtest/docker-compose.yml:86` 明确写了 `cpus: 2.25`。报告观测到 API CPU 峰值 **229.65%** —— 这正好是
**容器 cgroup 配额跑满**，不是 Node 单进程的架构上限。报告 §1 据此推出"Node 单进程在约 2.25 核处到顶，
横向扩展比继续堆内存更有效"，这个因果链**没有数据支撑**：

- 三个容器的配额是 API 2.25 + PG 1.5 + Nginx 0.25 = 恰好 4.0 核，是人为切分，不是自然瓶颈。
- 单进程的真实天花板可能更高（Node 主线程约 1 核跑 JS，Prisma 的 Rust 查询引擎有自己的 tokio 线程池，
  合计超过 2.25 核完全正常），也可能更低。**当前数据无法区分**。
- 直接后果：`450 RPS` 这个数字是"2.25 核 API"的容量，不是"4 核机器"的容量；而"多进程能带来多少收益"
  这个扩容决策的核心问题，上一轮**一次都没测过**。

**这是 V2 最重要的一个对照实验（见 S1 / T1 vs T2）。**

### 盲区 3 · 鉴权完全没跑

`docker-compose.yml:68-69` 设 `APP_JWT_REQUIRED: "false"`、`APP_JWT_SECRET: ""`，k6 直接发裸
`x-user-id: lt-user-0001`（`k6-readonly.js:50`）。`verifyUserToken()`（`server/src/services/userToken.ts:67-92`）
走的是"非 JWT 形原样放行"分支——HS256 验签一次都没执行。生产会执行。

### 盲区 4 · 覆盖面：只读、无写入、无报告渲染、无 LLM 业务路径

- `REPORT_PDF_DISABLED: "true"`（`docker-compose.yml:67`），且 `loadtest/Dockerfile:6` 设了
  `PUPPETEER_SKIP_DOWNLOAD=true`，**镜像里根本没有 Chromium**。而 Puppeteer 是进程内单例
  （`server/src/services/reportPdf.ts:66-86`），生产上它会和只读流量抢同一个进程的资源。
- 写入路径为零，`x-user-id` 白名单只读八个 GET。
- LLM 走 mock 且 mock 是**立即返回**的（`providers/mock.ts` 无任何延迟），队列、并发闸、排队等待
  这些行为一个都没被触发过。

## 2. 环境与拓扑

### 2.1 机器：建议临时按量付费 ECS，不要再清空生产机

上一轮为腾资源停了 8 个 AIStar 服务、MySQL、Nginx 和 2 个 Bossclub 容器，事后逐项验活恢复。这个操作风险高、
窗口紧，而 V2 的需求比上一轮更重：

- Q2 要求 API **不设 CPU 配额**，独占整机；
- PG 要独立出去（模拟 RDS），不能再和 API 抢核；
- Q9 的双实例场景需要两台机器。

按量付费开 2 台 4C8G 跑几小时的成本，远低于再停一次生产机的风险。**用完即释放。**

### 2.2 三档拓扑

| 拓扑 | API | PG | 入口 | 用途 |
|---|---|---|---|---|
| **T0 · 对照组** | 1 进程，`cpus: 2.25` | 同机，`cpus: 1.5` | Nginx `cpus: 0.25` | 完全复刻上一轮，验证 V2 环境与旧结果可比 |
| **T1 · 生产同构单进程** | 1 进程，**不设 cpus** | **独立机器/实例** | Nginx（生产配置） | 回答 Q2、Q4 |
| **T2 · 同机多进程** | 2 / 3 进程，不设 cpus | 同 T1 | Nginx upstream 多 server | 回答 Q3 |
| **T3 · 双实例** | 2 台 × T2 的进程数 | 同 T1 | ALB 或 Nginx LB | 回答 Q9 |

**T1 → T2 是本轮的核心对照实验。** 除进程数外所有变量必须固定：同一镜像、同一数据集、同一 k6 脚本、
同一 PG 实例、同一 `connection_limit`（按每进程算，总量对齐）。

### 2.3 配置原则：与生产同构，只隔离外部依赖

上一轮用 `NODE_ENV=test` 一把梭地关掉了一切，代价是连限流这种**生产必经路径**也被关掉了。V2 改为
**逐项显式隔离**：

| 项 | 上一轮 | V2 | 理由 |
|---|---|---|---|
| `NODE_ENV` | `test` | **`production`** | 让限流、安全告警等生产路径真正跑起来 |
| 限流 | 未注册 | **注册，用生产阈值** | Q1 的前提 |
| `APP_JWT_SECRET` / `APP_JWT_REQUIRED` | 空 / false | **随机密钥 / true** | Q4 的前提 |
| AI | `AI_PROVIDER=mock` | **不变** | `effectiveProvider==='mock'` 在 production 下同样短路，不触达真实模型 ✅ |
| 短信 / 微信 / 支付 / OSS / embedding / rerank | 凭据置空 | **不变** | 已经足够，继续沿用 |
| `PAY_SANDBOX` | false | **必须保持 false** | `assertSandboxSafe()` 在 production 下会拒绝启动，这是有意的护栏 |
| Redis | `REDIS_URL: ""` | **接隔离 Redis** | 限流 store、缓存、LLM 队列都要它 |
| `REPORT_PDF_DISABLED` | true | **参数化**，S4 置 false | Q6 的前提 |

> ⚠️ 切到 `NODE_ENV=production` 后，`server/src/index.ts:44-56` 的安全告警会检查
> `APP_JWT_SECRET` / `APP_JWT_REQUIRED` / `SMS_REQUIRE_CODE`。按上表设好即可静默；**若看到这些告警，
> 说明配置没生效，该轮数据作废。** 这是一条免费的自检。

### 关于 S5 的设计要点

上一轮 §5 有一条观察比 `semaphore=8` 这个数字重要得多：**20 并发触发 429 后，紧接着的 12 并发复测 48/48
全部 429，等窗口恢复后 8 并发才 80/80 成功。** 这说明上游是**滚动时间窗限额**，不只是瞬时并发限额。

所以 S5 不能只验证"并发不超过 8"，必须覆盖：

1. 稳态：并发 8 / 12，队列不积压，等待 P95 在阈值内；
2. 过载：并发 20 / 40，超出部分**入队**而不是直打上游，队列可见、可取消、15s 超时降级；
3. **窗口惩罚**：注入连续 429 后，全局闸应**整体降档并冷却**，而不是每条请求各自指数重试
   （`providers/claude.ts:38` 现在的 `maxRetries: 2` 在限额窗口里只会放大打击）；窗口恢复后应自动回升。

用 mock + 注入延迟做，**全程零 Token 成本**。真实上游只在 S8 复校时才碰。

### 关于 S8 的设计要点（本轮新增，原方案漏了）

上一轮探针固定 **1 字符输入 + `max_tokens=1`**，每次约 10 token；而生产实测单次 chat 是 **31,600 token**
（`SCALE_ARCH_PLAN` §0，input:output=33:1），差 3000 倍。所以「20 并发才 429」测的是**按请求数**的限额。

若上游实际是**按 token 数**（TPM）限，8 并发 × 约 2.4 次/分钟 × 31,600 ≈ **60 万 token/分钟**——
常见网关档位在 10 万–50 万，那么真实流量 **1–4 并发就会 429，而不是 20**。
**这直接决定 P0-2 的 `LLM_MAX_CONCURRENCY=8` 对生产是否成立**，必须测。

设计：
1. 分两组对照——A 组沿用 1 token 输入输出，B 组用**接近真实的 input 规模**（约 30k token，输出仍限小值控成本）。
2. 两组各跑并发阶梯 2 / 4 / 8 / 12，记录首次出现 429 的并发档。
3. **判据**：A 组 429 阈值远高于 B 组 → 上游按 token 限，`LLM_MAX_CONCURRENCY` 必须按 TPM 重算并考虑
   把 `LLM_RATE_MAX_PER_MIN` 从 0 打开；两组阈值接近 → 按请求限，8 可以保留。
4. **成本护栏**：B 组每次请求 input 就是 30k token，比上一轮整轮压测的 3,260 token 总量高得多。
   必须**先算预算再跑**，逐档核算、达预算即停，并沿用临时 `0600` 密钥文件与用后即删的约束。

### 关于 S4 的设计要点

必须**带只读底噪**。单独测报告渲染只能得到"能出几份报告"，而真正要回答的是"出报告时只读容量掉多少"——
这才是 P1-1 优先级的依据。做完 P1-1（Puppeteer 移出 API 进程）后**用同样参数重跑一次**，两组数据的差值
就是这项改造的收益。

## 6. 观测与指标口径

**原则：压测采集什么，线上就告警什么，命名一致。** 这是报告 §8 的明确要求，也是 S-b 提前做的理由。

| 层 | 指标 | 来源 |
|---|---|---|
| 客户端 | RPS、P50/P95/P99、错误率（分 4xx/5xx/超时）、按 endpoint 分解 | k6（`k6-readonly.js:54` 已有 `endpoint`/`run_id` tag，沿用） |
| 应用 | 在途请求数、事件循环延迟、各进程 RSS、GC | `/metrics`（S-b） |
| LLM | 队列深度、排队等待 P95、闸门占用、429 率、Token 消耗 | `/metrics`（S-b） |
| DB | 池 in-use/idle、总连接、active、idle-in-transaction、等待事件、慢查询 Top-N | `monitor.sh` + `pg_stat_statements`（L12） |
| 系统 | load、可用内存、swap、fd 数、网络 | `monitor.sh`（L12） |
| 入口 | 连接数、upstream 复用率、`limit_req` 触发数 | Nginx stub_status / 日志 |

采样保持 2s。**每档结束后立刻落盘并标注 `run_id`**，沿用上一轮 `loadtest/results/<run_id>.json` 的约定。

```
S0 烟测 ──▶ S0b 对照回归 ──┬─ 不可比 ─▶ 停，先排查环境差异
```

硬性中止条件（任一命中即停，排查后重跑该档）：

- 出现 OOM、进程重启或 PG 连接被拒；
- 错误率 >1% 持续 30s（k6 护栏自动触发）；
- 观测到 `NODE_ENV=production` 的安全告警（说明配置没生效，数据作废）；
- S8 真实 LLM 的累计 Token 达到当次预算。

| S4 | 8 并发出报告时只读 P95 劣化可量化；无 OOM。做完 P1-1 后重跑，劣化应显著收窄 |
| S5 | 20+ 并发不直打上游；注入 429 后自动降档、窗口恢复后回升；等待 >15s 触发降级 |
| S6 | 60min 内 RSS、DB 连接数、fd 数**无单调上升** |
| S7 | 摘实例零中断；主备切换恢复时间在预期内；上游 429 不扩散为用户可见错误 |

## 9. 安全约束

上一轮的约束执行得很好，**全部继承**：假数据与生产库物理分离、API 容器无公网出口、外部凭据置空、
独立 volume、精确清理、真实 LLM 用独立探针且受 Token 预算硬约束、密钥只放 `0600` 临时文件且用后即删。

V2 补充：

- **`APP_JWT_SECRET` 是压测专用随机值**，只存在于临时 env 文件，禁止写入仓库、报告或日志；
- **Redis 同样隔离**：独立实例、独立 volume、只挂 `backend` internal 网络；
- **临时 ECS 用完即释放**，释放前确认无数据残留；
- 清理仍只针对 Compose 项目 `junshi-loadtest` 及精确命名的 volume。
