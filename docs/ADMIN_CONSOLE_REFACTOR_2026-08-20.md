# 运营后台完整性审计与重构（2026-08-20）

## 1. 目标与范围

本轮按 `product-ui-completeness` 的实体、意图、动作、生命周期与异常恢复方法审计 `admin/`，范围包含支撑运营台的只读后台接口与共享契约。目标不是换皮，而是让运营能够回答三类真实问题：

1. 某个用户的一次会话发生了什么，消息、生成任务和模型调用能否在同一处核对？
2. 某个异常是谁、在什么请求、什么会话、什么时间触发，能否沿审计键继续下钻？
3. 经营/Token/调用统计能否按任意业务日期查看，并明确时区、比较口径和分页总数？

本轮不包含生产部署，也不改小程序；工作树中既有的 `app/weapp-native` 改动不在本次范围。

## 2. 改造前基线

| 等级 | 问题 | 运营后果 | 根因 |
|---|---|---|---|
| P0 | 没有跨用户会话工作台 | 只能看到用户的“会话数”，不能搜会话、读消息、核生成任务 | 后端没有 `/admin/sessions` 读模型，前端也无 section |
| P0 | 审计仅取最近 100-200 条后前端过滤 | 旧事件、特定请求和失败链查不到；搜索结果不是全量口径 | 缺少服务端日期、搜索、状态、分页接口 |
| P0 | 审计未把 request/session/operator 提升为正式字段 | Payload 里即使有线索也要人工翻 JSON，无法一步进入关联会话 | HTTP 元数据与业务展示契约断层 |
| P1 | 调用诊断固定 7 天，Token 固定 30 天且最大 90 天 | 月结、活动期、事故窗口无法按实际日期复盘 | 每页独立写死 `days` |
| P1 | 首页把近 7 天对比和 30 天成本混在同一屏 | 同一组卡片不是同一统计窗口 | 概览端点内部硬编码多个窗口 |
| P1 | 调用详情与若干列表行依赖鼠标 | 键盘无法可靠打开/关闭详情，焦点不会归还 | 详情不是完整 dialog 生命周期 |
| P2 | 各页重复 7/30/90 chips | 时区、文案和自定义日期能力不一致 | 缺少共享日期控件与服务端解析器 |

## 3. 重构后的产品模型

### 3.1 会话工作台

- 实体：会话、用户、租户、顾问、项目、消息、生成任务、LLM trace。
- 主意图：按日期/状态/关键词找到会话，判断是否在途或失败，打开详情核对全文。
- 元数据：消息角色计数、生成/失败数、最近消息、创建/更新时间、会话/用户/租户/项目 ID。
- 生命周期：空会话、正常会话、生成中、曾失败、已完成；消息支持游标读取更早记录。
- 恢复：列表与详情各自有 loading/error/retry；加载更早失败不清空已读消息。
- 次动作：从会话详情直达用户；生成与 trace 留完整排障 ID。

接口：

- `GET /api/admin/sessions?from=&to=&q=&status=&agentKey=&page=&pageSize=`
- `GET /api/admin/sessions/:id?before=&limit=`

### 3.2 审计链路

- 新接口 `GET /api/admin/audit-view` 使用数据库服务端筛选与精确分页；旧数组接口保留兼容。
- 正式筛选维度：日期、用户/后台行为、成功/失败、action、userId、全文关键词、监控抓取开关。
- 正式展示键：`requestId`、`sessionId`、`operator`、用户/租户、方法/路径/状态、IP/UA。
- 新产生的 `admin.http` 自动记录后台操作者种类、账户 ID/用户名/角色，不记录 token。
- 详情可按 request ID 收敛同一请求链，并可直接打开关联会话或用户。
- `/api/metrics` 历史噪声继续默认排除，显式开启才显示。

### 3.3 统一时间范围

- 共享 `DateRangeFilter` 提供近 7/30/90/365 天和自定义起止日期。
- 服务端 `parseAdminRange` 是唯一解析入口；自定义日期按 `Asia/Shanghai` 自然日解释，返回 ISO 边界与展示日期。
- Token、调用诊断、会话、审计和经营概览共用该口径；自定义窗口最长 3660 天。
- 经营概览改为“所选区间 vs 前一等长区间”，主值、环比和副文案保持同一指标：区间值作主值、累计值作补充，不再拿累计主值配区间环比，也不再混用固定 7 天与 30 天。
- Token 日聚合按上海时区分桶，避免 UTC 日界把凌晨数据分到前一天。
