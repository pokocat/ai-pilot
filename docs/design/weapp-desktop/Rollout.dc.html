三个要盯住的风险
1WXML 加一层 wrapper 会打断现有选择器
现有样式里有不少 .exec-page > view 这种直接子选择器。副栏一包，被包住的那几块就不再是直接子元素。 对策：包之前先把每个页面的直接子选择器扫一遍，改成不依赖层级的写法， 这一条单独一个提交，与布局改动分开。

连带的设计约束：wrapper 只能收「在手机上本来就相邻」的块 —— 包一层就意味着它们在窄屏只能出现在一个位置。战局的天时、图籍的主 CTA 因此留在主栏， 换来的是手机版一个节点都不动。
2底栏隐藏后的 overlay 记账
setOverlay 是按 key 成对记账的（问策的浮岛就用它）。桌面档隐藏底栏时如果只加不减， 窗口缩回手机宽时底栏就再也回不来了。 对策：用独立 key desktop-rail，在 syncRail 那种「值变了才动」的地方成对开关。
3本地验不了真机
开发者工具模拟器只给手机宽度，微信 PC 的真实窗口没法在本地驱动。 对策：排版继续用 npm run preview:desktop（抓真渲染 WXML + 真编译 WXSS）在 960/1008/1280/1440 逐档核； 但导航条和底栏隐藏这两件事必须传体验版，在你的桌面微信上实看。 建议第二步做完就发一版。
要你拍板的三件事
决策 A：走方案乙（左侧 72px 导航条）？
我推荐乙。选甲的话第二步只剩断点和容器，第三步不变。
决策 B：副栏固定 320 / 主栏弹性 / 正文轴 840？
主栏 = 窗口 − 456，到 1440 撞上容器 1240 封顶后定格 896，正文轴 840 从这里开始生效； 再宽的窗口只增加两侧留白，正文行长在任何显示器上都一样。 如果你更想「窗口越大内容越多」，那是另一套（副栏也弹性、正文轴不封顶），我可以改。
决策 C：双栏门槛定在 960？
按你截图那个窗口（约 1008pt）倒推的。如果你平时是最大化用，门槛可以更高、副栏可以更宽； 告诉我你常用的窗口大概多大，这个数就能钉死。
确认后我按这个顺序干
先把「直接子选择器」那一条清干净（独立提交）→ 第二步骨架 → 发一版体验版给你在桌面微信上看导航条 → 你点头之后再做第三步四个 tab 的归位。
